# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Sencha QA (Auto Tester) — an AI-powered QA automation platform. Users create projects, import test cases from TestRail (a whole suite or a single run) and run them through an AI agent that controls a remote machine (via a WebSocket-connected controller client) to execute tests against real applications.

## Session start

At the beginning of every session, before doing anything else, read the notes in
`docs/changed/` (newest first by filename date) to learn what has changed recently
and why. They are short by design; read them all, or at least those newer than the
last commit you already know about. Also skim `docs/plan/` for plans whose Status
is not `Done`, since those describe work in flight. Older history lives in
`docs/specs/` (requests) and `docs/impl/` (implementation notes and plans).

## Workflow

Every code change follows the loop in `.claude/rules/workflow.md`:
plan (`planner` agent, `docs/plan/`) -> implement (independent parts in
different files go to parallel sub-agents, then the orchestrator integrates and
does a final pass) -> `reviewer` + `verifier` in parallel -> fix -> repeat review
until clean -> document in `docs/changed/`.

## Conventions

- One Django app per domain. Business logic goes in the app's service layer; new
  use cases go in `<app>/services/<use_case>.py` (as in `agents/services/`).
  `accounts/services.py`, `projects/services.py` and `dashboard/services.py` are
  legacy single-module services: do not add unrelated use cases to them.
- Views, WebSocket consumers and Celery tasks are thin: validate input, call a
  service, map domain errors to responses. They never touch the ORM directly and
  hold no business logic.
- No REST API: the one machine surface is the MCP gateway (`mcp_gateway`, Manual runs + KB reads). Otherwise server-rendered HTML with the Django template engine, data passed
  via template context, input through Django forms. Alpine.js only for sockets and
  small UI behaviour (dialogs, tabs, hamburger menu, ...).
- Domain errors are plain exception classes in `<app>/exceptions.py`.
- Security: every sensitive view requires authentication; project views use
  `@project_membership_required` for authorization; login and other credential
  surfaces are throttled; no XSS (`|safe`/`mark_safe` on user data), SQL, shell or
  other injection.
- Custom user model (`accounts`); keep it extensible.
- All imports at module top level; no lazy imports. Full type annotations
  everywhere; mypy runs in strict mode for the server and, with its own config,
  for `controller_client/` and `vision_worker/`. No skipping types.
- Settings: every env var is read in `settings.py` via `python-decouple` (never
  import `decouple` elsewhere, never read `os.environ` in app code). All service
  configs (db, redis, LLM, ...) come from `.env`; keep `example.env` up to date.
  `STATIC_URL`/`STATIC_ROOT` and `MEDIA_URL`/`MEDIA_ROOT` are both defined.
- Celery uses redis as broker, `django-celery-results` as result backend and
  `django-celery-beat` for schedules.
- This project does not contain test cases. Do not add `tests.py`, `tests/`
  packages, or test tooling; verify changes with the type checker and manual
  smoke checks instead.

## Commands

```bash
# Dev server (ASGI via Daphne, required for WebSockets). Daphne caps incoming
# WebSocket messages at 1 MiB by default and closes the socket (code 1009) on
# anything bigger; controller screenshots / vision worker parse results are several MiB,
# so always pass the two size flags (docker-compose.yml already does). Plain
# `runserver` cannot raise that limit — use it only when no controller connects.
python -m daphne -b 0.0.0.0 -p 8000 --websocket-max-message-size 33554432 --websocket-max-frame-size 33554432 auto_tester.asgi:application
python manage.py runserver              # no controller traffic only (1 MiB WebSocket cap)

# Celery workers (five separate queues)
celery -A auto_tester worker -Q upload -l info -n upload@%h
celery -A auto_tester worker -Q execution -l info -n execution@%h
celery -A auto_tester worker -Q notify -l info -n notify@%h
celery -A auto_tester worker -Q assist -l info -n assist@%h      # readiness Scan / Check machine
celery -A auto_tester worker -Q knowledge -l info -n knowledge@%h --concurrency=2 --max-memory-per-child=1048576   # knowledge base extraction (macOS dev: --pool=solo)
celery -A auto_tester beat -l info --scheduler django_celery_beat.schedulers:DatabaseScheduler

# Type checking (strict mode)
mypy .                                  # runs with strict=True, excludes venv|migrations|controller_client|vision_worker
controller_client/.venv/bin/mypy --config-file controller_client/setup.cfg controller_client/  # separate venv/config
vision_worker/.venv/bin/mypy --config-file vision_worker/setup.cfg vision_worker/              # separate venv/config

# Infrastructure
docker compose up db redis searxng -d   # minimal local services
docker compose up -d                    # full stack including nginx, celery, flower
scripts/verify_server_image.sh          # build the server image and assert it can import the shared controller protocol and package the controller ZIP

# Controller client diagnostics (run on the controller machine, inside its venv,
# from the directory that contains controller_client/)
python -m controller_client.diagnose    # screen capture
python -m controller_client.diagnose --browsers   # launch each browser (or --browsers firefox,msedge) and report what is missing
python -m controller_client.diagnose --input      # screen scale vs OS, pointer mapping, scroll direction, stuck modifiers; prints a summary block to paste back (--no-interactive: automatic checks only)

# Vision worker (on the GPU machine, inside vision_worker/.venv, from the repo root; see vision_worker/README.md)
python -m vision_worker.main            # connect to VISION_SERVER_URL and serve parse requests
python -m vision_worker.diagnose        # imports, weights, device, model load, one inference, result size

# Formatting and typing — same checks pre-commit runs
pre-commit run --all-files

# Migrations — review models first and warn about any data loss before migrating
python manage.py makemigrations
python manage.py migrate

# Dependencies — NEVER use pip freeze. Find on PyPI, add to requirements.txt as x~=1.0.1, then:
pip install -r requirements.txt
```

## Architecture

### controller_client

- **controller_client/** — Standalone Python client that runs on target machines. Connects to the server via WebSocket, receives action commands (click, type, screenshot, browser actions), and replies with results. Own venv/dependencies and own strict mypy config; it no longer runs OmniParser (see vision_worker below). The handshake carries `client_version` + a typed capability list (`controller_client/protocol.py`: `CLIENT_VERSION`, `ClientCapability`, `REQUIRED_CLIENT_CAPABILITIES`); the server rejects controllers missing a required capability before marking the project connected. The tracked `controller_client/` source must stay inside the server Docker image (shared protocol import + ZIP download); only its venv, `.env` and `logs/` are `.dockerignore`d. On Windows, input actions (click/hover/drag/scroll/type/key) first run `controller_client/input_guard.py`: UIPI makes Windows silently drop injected input while an elevated window (Task Manager, installers, anything past a UAC prompt) is in the foreground, and pyautogui never notices — the guard raises `InputBlockedError` instead so the agent sees a failure rather than a phantom "Clicked". Run the controller as Administrator when tests need to drive elevated apps. Optional capabilities (checked where used, not at handshake): `BROWSER_SELECTION_V1`, `DOUBLE_CLICK_V1` (`double_click`, `browser_double_click`; a case needing it on an older runner asks for help with the fault `runner_outdated`), `CLOSE_APP_V1` (`close_app`, `close_tab`, in `controller_client/app_closer*.py` + `app_close_policy.py`), `WINDOWS_SHELL_V1`, `SCROLL_V1` (`scroll`; an older runner gets a tool error with a key_press fallback, not a help request) and `ARTIFACT_SCAN_V1` (`scan_directory`, `inspect_paths` in `controller_client/artifact_scan.py`, CLIENT_VERSION 0.11.0; stat only, never follow symlinks or junctions, network paths refused unless the server sends `allow_network`) and `POINTER_MODIFIERS_V1` (CLIENT_VERSION 0.24.0, desktop only: optional `modifiers` — `primary` = Cmd on macOS / Ctrl elsewhere, `ctrl`, `shift`, `alt`, `meta` — held during `click`/`double_click`/`hover`/`drag`/`scroll` and always released; older runners ignore the field, so the server refuses first: Need help `runner_outdated`, MCP `[machine_outdated]`; macOS posts its own flagged Quartz events in `macos_pointer_events.py`). **Kept command sessions** (`KEPT_SESSIONS_V1`, CLIENT_VERSION 0.21.0; `docs/changed/2026-11-08-mcp-machine-tools.md`): `start_interactive_cmd` with `keep`/`max_seconds`/`max_kept`/`initial_read_ms` starts a kept session next to the agent's single foreground session (never replaced by a later start; ≤ `KEPT_SESSIONS_MAX` = 4, ≤ 4 h; a daemon reader drains it into a 1 MiB `kept_output_buffer.KeptOutputBuffer`, `output_dropped` flags discarded output), `list_interactive_sessions` lists them; a start without the keep fields is the unchanged agent path. Wording is "kept session", never MCP. **Web browser layer** (`WEB_BROWSER_V1`, CLIENT_VERSION 0.22.0; `docs/plan/feat-mcp-browser-toolset.md`): WebDriver-based `web_browser_*` messages answered by `web_browser_result`, separate from the Playwright `browser_*` path (never imports it). One table `protocol.web_browsers_for(target, host_os)` (Windows Chrome/Edge/Firefox, Linux Chrome/Firefox, macOS Safari/Chrome/Firefox, Android Chrome/Edge/Firefox, iOS all four). `web_browser_hub.WebBrowserHub` (daemon `web-browser` worker, budgets; a browser whose call overran is refused as busy until that call returns) acts only on a browser already open and controllable: named → that one, unnamed → the single open one, else `WEB_BROWSER_NOT_OPEN` / `WEB_BROWSER_AMBIGUOUS`; only `web_browser_open` starts one. Desktop (`web_browser_desktop.py`, Selenium + Selenium Manager, `CONTROLLER_WEB_DRIVER_DOWNLOAD`) attaches to browsers started by `web_browser_launch.py` with the dedicated profile `controller_client/web_profiles/<browser>/` and loopback remote control (also the person's shortcut `<base>/open-test-browser.sh|.cmd`, written by setup and self-update; profiles excluded from the bundle and moved by a self-update); Safari is a safaridriver session. Android (`web_browser_android.py`): chromedriver attached to the running Chrome/Edge over ADB, geckodriver session for Firefox. iOS (`web_browser_ios.py`): web view contexts of the existing XCUITest session inside `MobileDevice.web_call`, back to NATIVE_APP in `finally`; accessibility mode (`web_browser_accessibility.py`) when a page is not inspectable. `diagnose --web-browsers` checks the desktop cells. Not yet run on a real browser or device. **Window capture** (`WINDOW_CAPTURE_V1`, CLIENT_VERSION 0.20.0; `list_windows`, `capture_window`): `window_capture.py` (service), `window_capture_policy.py` (allowlist, deny list of runner/terminals/shells, selection, `unobscured_by_stacking`, screen rule), platform modules per `capture_platform.py` (Windows `win32_*` / `window_grab_windows`, macOS `*_macos`, X11 `x11_*` / `*_x11`, Sway/Hyprland `wayland_wlroots`, GNOME Wayland and Xorg `gnome_shell_capture` + the bundled extension `gnome_capture_helper/` (token-authenticated, installed by setup and self-update; one re-login)). It switches to a window's virtual desktop and back (`desktop_switch.py`, freshness check), and fails closed: overlays and windows with unknown pids count as foreign; KDE Wayland is refused. `python -m controller_client.diagnose --capture` checks it. `close_app`/`close_tab` fail closed: they never close the runner's own process, its terminal (ancestor or any known terminal host) or the OS shell, and `close_tab` refuses unless it can prove the front tab is not the runner's. Every pointer action maps screenshot pixels to the input backend's coordinates in `controller_client/executor.py` (`pointer_mapping.map_to_input`, per-axis scale from `capture_size()`/`input_size()`; equal sizes change nothing), so the server always sends screenshot-pixel coordinates. **Manual runs** (`MANUAL_RUN_V1`, CLIENT_VERSION 0.13.0): the person window's "Manual run" tab (`person_window_manual.py`, `manual_coordinator.py`); every capture goes through `manual_capture.py` (confirmed hide via `hidden_for_capture`, else no capture; downscaled to `MANUAL_SHOT_MAX_PIXELS` / `MANUAL_SHOT_MAX_BYTES`), shots and hand-ins live in `controller_client/manual_spool/` (`manual_spool.py`, `CONTROLLER_MANUAL_SPOOL_MAX_MB`, excluded from the ZIP/update bundle) and `manual_uploader.py` uploads them after the hand-in, resuming after a disconnect or restart; `update_runner` is refused while the spool has files. **Self-update** (`SELF_UPDATE_V1`, runners ≥ 0.8.0; older ones need one last manual update; `docs/plan/feat-runner-self-update.md`): a member presses Update Test Runner on the Environment Connection card (`projects/runner_update_*`, one in-flight `RunnerUpdate` per project, expired after `RUNNER_UPDATE_TIMEOUT_SECONDS`; Start/Resume/machine setup refuse while one runs). The server sends `update_runner` with the cached `projects.runner_bundle` ZIP (no `.env`, ≤ `MAX_UPDATE_ARCHIVE_BYTES`, sha256) over the runner's own socket. The runner installs it side by side (`controller_client/update_*.py`): safe extract into `<base>/test-runner-<version>/` (`<base>` = parent of a managed `test-runner-*` root, else the install root), copied `.env`, own venv + pip + `playwright install` (no `--with-deps`, no OS packages), rewrites `<base>/start-test-runner.sh|.cmd`, and spawns the new runner detached (Windows: new console, elevation kept; POSIX: background, log in `controller_client/logs/`), reporting `update_status` phases. The new runner's handshake supersedes the old one (4001, normal exit; no new server logic), then it deletes the old folder after the old PID exits (`update_cleanup.py`, path from the old process, never the server). No rollback: if the new runner never connects, the old one reports `failed` and stays connected. **Person steps** (`PERSON_STEPS_V1`, Human in the loop): a separate Tk window process (`controller_client/person_window*.py`, `person_window_ipc.py`) shows the project's open person steps and sends the answer; `_dispatch` hides it before every agent action (`hidden_for_action`) and it never takes focus. `CONTROLLER_PERSON_WINDOW` / `CONTROLLER_PERSON_EMAIL` are asked at the first interactive start and saved in `.env`; `python -m controller_client.diagnose --window` checks it. **Window v2** (`PERSON_CASE_CONTEXT_V1`, `PERSON_DISCUSSION_V1`, `CASE_PAUSE_V1`, CLIENT_VERSION 0.12.0; `docs/changed/2026-10-31-runner-person-window-v2.md`): `person_step_state.cases` adds the step's case (test case, log tail), a Need help case waiting for a person with its discussion, and the running case (Pause only); the window has Step / Test case / Log / Discussion tabs, copyable read-only text and A−/A+ (`CONTROLLER_PERSON_WINDOW_TEXT_SIZE`). Runner messages `case_pause_action` → `runner_case_pause_services.pause_from_runner`, `person_chat_send` → `machine_setup/services/runner_discussion.send_from_runner`, `person_help_action` → `projects/runner_help_action_services.resolve_help_from_runner`; the snapshot is composed in `projects/runner_window_state.py` (imported only by the consumer), nudges coalesced to one push per second. Help resolutions and chat sends take a `PersonStepActor` (`CaseHelpRequest.resolved_via` / `resolved_by_label`, `SetupMessage.author_label`)

### Phone and tablet targets

- **Phone runner** (`MOBILE_DEVICE_V1`, CLIENT_VERSION 0.19.0; `docs/changed/2026-11-06-mobile-device-runner.md`): `CONTROLLER_TARGET=android|ios` makes the Test Runner on a host computer drive one phone, tablet, emulator or simulator (`CONTROLLER_DEVICE`) through Appium 3 (`controller_client/mobile_*.py`; managed Appium on 127.0.0.1 unless `CONTROLLER_APPIUM_URL`). `controller_client/target.py` holds the selected backend (`get_target_backend`, `get_mobile_device`); the phone backend implements `DesktopBackend` + `MobileDevice`, so screenshots, `click`/`click_at`, OmniParser and Manual capture are unchanged and `pointer_mapping` converts iOS pixels to points. `system_info.os` stays the host OS; the device keys (`parse_device_info`) are stored only when the capability is advertised, and a non-blank `Project.agent_device_state` marks a phone runner. The agent's tools come from `tool_definitions_for(ToolContext.runner_target)` (no `hover`, `close_tab`, `browser_*`; phone tools in `agents/services/tools_mobile.py`); shell commands run on the host with `$RUNNER_DEVICE_ID`. `device_status` heartbeats (`device_monitor.py` → `runner_device_status_services`) drive `MachineState.DEVICE_OFFLINE` ("Phone disconnected", one rule: `projects/runner_target.device_machine_state`), which blocks runs and setup sends; `DeviceDisconnectedError` opens Need help with fault `device_disconnected` (current screen). Not yet run on a device.
- **Capture app picker** (`DEVICE_APPS_V1`, CLIENT_VERSION 0.23.0; `docs/changed/2026-11-08-capture-phone-app-picker.md`): phone runners answer `list_device_apps` with `device_apps_result` (`controller_client/device_apps.py`, `MobileDevice.installed_apps`; ids normalized, iOS names, Android ids only). The Settings "Screenshot capture" card's "Pick from the phone's apps" (`projects/capture_phone_apps_services.py`, synchronous ≤ 30 s, refused while an agent run is Started, one load per project) shows them; ticked ids are merged by `project_capture_apps_services.add_capture_allowed_processes`. `stored_capture_apps` is the one reader of `Project.capture_allowed_processes`.

### vision_worker and visual_engine

- **vision_worker/** — Standalone GPU client running OmniParser (vendored in `vision_worker/omniparser/`, weights `.gitignore`d), own venv/requirements/strict mypy config. Set up with `vision_worker/scripts/setup.sh` / `setup.ps1` and run with `python -m vision_worker.main`, like the Test Runner; one process per GPU (`CUDA_VISIBLE_DEVICES`). No Docker. Connects out over wss to `ws/vision-worker/` with the shared `VISION_WORKER_TOKEN`, preloads the model, reports `status` (loading/ready/failed; also a 30 s heartbeat) and answers `parse_request` with elements + an annotated image; it answers `BUSY` beyond 1 running + `VISION_MAX_QUEUE` queued. Wire protocol in `vision_worker/protocol.py` (stdlib only; the server imports it, so the source stays in the server image).
- **visual_engine** (Django app) — global, not per project. `VisionWorker` rows (one per worker name; newest connection wins, stale after `VISION_WORKER_STALE_SECONDS` without a heartbeat), `VisionWorkerConsumer`, and services: `parse_screenshot` rotates over ready workers round robin with a Redis counter (shared by all Celery processes), skips busy ones and retries disconnects within `VISION_PARSE_BUDGET_SECONDS`. `projects.services.controller_find_elements` = runner `controller_screenshot` + `parse_screenshot`. Run/resume/re-run/machine-setup gating and the machine badge need at least one ready worker (`MachineState.VISUAL_ENGINE_OFFLINE` when none is connected).

### Need help (human in the loop)

- When a step fails for an environmental reason, the orchestrator decides `need_help` instead of failing. The case goes **Need help** (`need_help`), the run **Needs help** (`TestRunStatus.PAUSED`, in `ACTIVE_RUN_STATUSES`), and a `CaseHelpRequest` is opened. The worker exits; the chain's remaining tasks stand down on PAUSED. No teardown or cleanup, so the machine stays as it was.
- Per-run `help_mode`: **Attended** notifies project members (ntfy) right away; **Night** first opens a Machine setup auto-fix thread (`SetupConversation.kind=auto_fix`, `report_case_fix` tool, existing limits only), then falls back to a person if not fixed. One auto-fix per step per from-scratch execution (`projects/case_help_policy.py`). The mode can be switched mid-run (`projects/run_help_mode_services.py`).
- Only a person marks a case Blocked: Mark blocked (always `help_skipped`, the only literal Blocked write) or an applied result change to Blocked (`person_review`, assigned from a variable). Infrastructure faults (runner lost or unresponsive, visual engine, AI service, time limit, browser unavailable, runner outdated, resume state lost, internal error) never block a case: the worker opens a help request with `CaseHelpRequest.fault` (`projects/case_faults.py`), and Night mode lets the auto-fix agent decide whether it can fix it.
- Continue / Mark failed / Mark blocked / Stop auto-fix in `projects/case_help_services.py`. Continue follows `CaseHelpRequest.continue_mode`, decided when the case paused (`projects.case_faults.help_continue_mode`): `current_screen` writes the checkpoint `help` key with `continue_pending` (re-run the failing step, no cleanup or restore), `restore` writes it without (cleanup and restore sub-task first; runner faults, or any fault before a due restore finished: `restore_baseline` in `execute_test_run_test_case`), `from_scratch` clears the checkpoint (no checkpoint was saved yet). The setup agent's and the person's notes reach the case's state except from scratch.
- **Help chat** (`docs/changed/2026-10-24-help-chat.md`): from a Need help case a person opens a multi-turn chat (`machine_setup:help_chat_open` → a `SetupConversation` thread of kind `case_help`, or the request's existing auto-fix thread; one thread per help request). Person turns there get the `CASE_HELP` role (`machine_setup/thread_role.py`): `run_setup_task` (full machine) plus `get_help_case`, `propose_plan_change` and `propose_resolution`. A redesign is a whole new plan whose leading steps may be *carried* from earlier steps that passed (`agents/plan_revision.py` validates: strictly increasing prefix, each once, at least one step runs); it is a `CasePlanRevision` draft until the person presses Continue with "Use the redesigned plan" ticked, then the case resumes at the first step not carried, with no cleanup or restore. The agent's suggestion is shown only, never pre-filled or sent to the tester. The Night auto-fix turn has no plan tools.
- **Pause and discuss** (`docs/changed/2026-10-31-pause-and-discuss.md`): a writable member pauses a running case, or a case whose person step waits (`projects:test_run_case_pause`, `projects/case_pause_services.request_case_pause(actor=PersonStepActor)`; runner seam `runner_case_pause_services.pause_from_runner`, owner-only, shared 20/min runner throttle). A running case stores the request on its row (`TestRunTestCase.pause_requested_*`, `pause_message`, for one `execution_generation`); `_build_cancellation_check` sees it and the worker opens a Need help request with `stopped_by_pause` (`projects/case_pause_rows.open_pause_help_request`, shared with the waiting-step conversion). A pending pauser beaten by need_help or a fault is still recorded (`paused_by*`, `has_pending_person`): no Night auto-fix, no ntfy. On commit `machine_setup.tasks.open_paused_help_chat` (sent by name) opens the `case_help` thread and sends the first message as the pauser (`pause_message_state` pending/sent/refused/dropped); the case page navigates there via `discussion_url`. A verdict that wins keeps a message as "Too late to pause" (result chat pre-filled, or Dismiss). Lists keep "Need help"; no credit or session activity for the pause itself.
- **Continue mode** for every help request: the person picks one of `projects/case_pause_policy.allowed_continue_modes` (current screen withheld when the stored mode is restore; restore needs a cursor past step 1; from scratch always), enforced in `continue_after_help(continue_mode=)`; a redesign requires current screen and is refused on a restore request. The help-chat agent may suggest one (`propose_resolution(continue_mode=)`, `agent_proposal_continue_mode`), shown only. The Night auto-fix keeps the stored mode.
- **Result chat** (`docs/changed/2026-10-26-case-result-chat.md`): from a Passed / Failed / Blocked case a person opens a multi-turn chat (`machine_setup:result_chat_open` → one non-archived `SetupConversation` of kind `case_result` per case, `result_case` FK). Its turns get the `CASE_RESULT` role: `run_setup_task` (full machine) plus `get_case_result`, `read_case_log`, `ask_case_screenshot`, `propose_result_change` and `propose_plan_change`. Proposals are cards (`CaseResultChange`, or `CasePlanRevision` with `source=review` and no help request); only a person's Apply (`projects/case_result_change_services.py`: new status + server header + summary, Checked/Sent cleared) or "Re-run with redesigned plan" (`projects/case_review_redesign_services.py`: Resume path via `run_reopen_services`, cleanup + restore of carried steps, then step C+1) acts. Sends are refused while a run is Started (not Paused) or the machine is not READY. Stale cards are refused by fingerprints.
- **Force stop** (`docs/changed/2026-10-31-setup-hard-stop.md`): `MACHINE_SETUP_FORCE_STOP_GRACE_SECONDS` after Stop, a writable member force-closes a running setup turn (`machine_setup/services/force_stop_turn.py` → `live_turn.close_live_turn`, then Celery revoke SIGTERM). The worker writes nothing once its turn is not RUNNING (`run_turn._finish` locks the turn row); keep every new worker write to the turn or transcript gated the same way.
- `projects.services` must never import `machine_setup.services` (cycle): use the leaf modules `machine_setup.task_names` / `auto_fix_stop` / `turn_state` and `send_task` by name. A beat sweep (`machine_setup.tasks.sweep_stale_auto_fixes`, `notify` queue) settles lost or dead auto-fixes.
- **Human in the loop** run mode (`RunHelpMode.HUMAN_IN_THE_LOOP`, stored `"hitl"`; `docs/changed/2026-10-28-hitl-run-mode.md`): a person performs every step. The agent plans, prepares each step for a person (`agents/services/person_steps.py`; a command only when the case states it as a whole, shell label from the runner's OS via `agents/os_shell.py`), the case goes `awaiting_person`, the run PAUSED (`RunHelpState.PERSON_STEP`), and a `CasePersonStep` row is opened. The person reports from the "Your turn" card (`projects/person_step_services.py`: report, overrule, mark failed, mark blocked); the re-queued worker confirms with a sub-agent limited to `take_screenshot` / `execute_command` / `wait_for_command` (read-only by prompt), records a `performed_by="person"` attempt and hands out the next step. Not confirmed → back to the person; "different" → step failed; the case continues unless a remaining step depends on it, and the verdict decides whether such differences fail the case (passes only when the AI is sure they do not touch what the case checks). The checkpoint `person` key carries the hand-off and report; rows are settled from the checkpoint save hook (`projects/person_step_rows.py`). No AI teardown, no Night auto-fix; faults still open Need help. **Evidence** (`docs/changed/2026-10-31-hitl-failure-evidence.md`): every confirm attempt has a screenshot (taken without the model when it took none); a "different" report records the pasted and check outputs (head and tail, `PERSON_EVIDENCE_OUTPUT_MAX_CHARS` each, fenced) as `SubTaskResult.error`, one `[Evidence]` log block and in the TestRail step list. Mark failed / Mark blocked keep the row `reported` with the mark's close reason, write the `person` key `marked_failed` / `marked_blocked` and queue the case: the worker (`projects.services._finish_person_mark` → `agents/services/person_mark.py`; `PERSON_EVIDENCE_LLM` off = screenshot only) records a failed person attempt, then writes the person's verdict (`projects/person_mark_verdict.py`). Any fault, or a gate refusing the queue, keeps the verdict and logs "[Evidence] no evidence: …"; never Need help. An overrule takes no screenshot. Switching away hands a waiting step back to the agent (current screen). Resume, help Continue (except current screen) and plan redesigns drop the `person` key. **Answers from the Test Runner** (`projects/runner_person_step_services.py`): the consumer pushes `person_step_state` (≤ 5 steps, no reopen blockers; one query) and takes `person_step_action` only from the project's owner connection, throttled to 20 answers/min/project; the same `person_step_services` rules apply. ### Key Patterns

**TestRail screenshot review** (`docs/changed/2026-11-03-testrail-evidence-relevance.md`): the screenshots attached to a TestRail result (agent and Manual cases) are chosen by an AI review, not by position. Checking a case (`projects/testrail_evidence_services.prepare_testrail_evidence`, query-only) marks it `done` when it has nothing to review (no candidates, or no source run) or a still-matching review (`TestRunTestCase.evidence_review_key`), else `pending` and queues `projects.tasks.review_testrail_evidence` (`upload`). `projects/testrail_evidence_review_services.py` sends the candidates (agent: shots of the causing attempts, ≤ `TESTRAIL_EVIDENCE_REVIEW_MAX_IMAGES`, with the causing step's log excerpt; Manual: hand-in shots with the tester's marks and notes) to `agents/services/evidence_review.py` and writes `TestRunScreenshot.relevance` and the `testrail_evidence` flags under run then case lock, only while `testrail_source_result_id` is null. None relevant → nothing attached (the comment says so). A case whose review is not `done` and current never gets a new TestRail result: `push_checked_results` rewrites manual notes, reviews inline (600 s), then rechecks right before planning; AI faults leave the case checked and unsent ("Screenshot review failed", Retry: `projects:testrail_evidence_review_retry`). No on/off setting.

**TestRail case send** (`docs/changed/2026-10-30-early-failed-testrail-push.md`): a writable member sends Failed cases to their source TestRail run (run-link imports only) as soon as they fail, also while the run is Running/Paused, from the run page, case page and `/failures/` (`projects/testrail_case_send_services.start_case_send`: check + send exactly the selected cases, same per-run slot and task as "Send checked", which stays finished-only). Paused-run wake paths (help Continue, person step report, Continue run) use `run_reopen_services.list_wake_blockers` and are not stopped by a live send; Resume / Re-run / Reset / Uncheck / Apply still use the push blockers.

**Controller Protocol**: The controller client on the target machine connects via WebSocket. The server dispatches actions (click, type, screenshot, browser commands) through the channel layer and waits for replies. All controller actions are in `projects/services.py` (functions prefixed `controller_*`).

**Authorization** (`docs/changed/2026-10-29-user-management.md`): `@project_membership_required` in `projects/decorators.py` handles `@login_required` and membership in one query (`project_access_services.get_project_access`) and passes a resolved `project` kwarg. Membership has a role (`ProjectMembership.role`: `ProjectRole.MEMBER` / `READ_ONLY`; `WRITABLE_ROLES` is the one source for "can write"): the decorator answers 403 to a read-only member on any method other than GET/HEAD/OPTIONS, so every write view must be POST and decorated; `project_read_access_required` is the only opt-out (Leave). Views that cannot take the decorator use `decorators.get_writable_project`. Templates get `project_can_write` from `projects.context_processors.project_access` (undefined, so falsy, outside decorated views). Writable members invite (optionally read-only), change roles and leave on the Settings tab (`projects/project_member_services.py`); a project always keeps at least one active writable member. Read-only members get no notifications, inbox or attention items, and a Test Runner email of a read-only member answers anonymously. Active superusers have implicit writable access to every project (`docs/changed/2026-11-01-admin-all-projects.md`): `get_project_access` grants it when `projects.project_access.has_superuser_project_control` (the one predicate) holds, so every decorator and project WebSocket (`get_project_for_user` delegates to it) follows; `ProjectAccess.is_admin_access` drives the "Admin access" badge. They are not members: notifications, inbox, attention, dashboard, `/failures/`, `/projects/`, runner email matching and the last-writable-member invariant stay membership-only. The superuser-only `/all-projects/` page (`dashboard:all_projects`, `dashboard/services/all_projects.py`) lists every project with search and filters. The flag also unlocks the Users page (`/accounts/users/`, `accounts/user_management_services.py`) and choosing or changing a run's help mode (`projects/run_help_mode_policy.resolve_help_mode`, called under the run lock by every service that writes `help_mode`; others keep the stored mode). New runs take the project's run mode (`Project.default_help_mode`, Human in the loop by default; re-run as a new run too); a superuser changes it on the Settings "Run mode" card (`projects/project_run_mode_services.py`), optionally applying it to drafts, active runs (one by one through `change_run_help_mode`) or all runs.

### Frontend

- User-facing brand is **Punk Hazard** (internal package names stay `auto_tester`). Brand assets in `static/branding/`; `brand_name`/`brand_tagline` come from `auto_tester/context_processors.py`
- Own design system, no Tailwind: `static/css/punk-hazard.css` (dark-first tokens + component classes — `.btn-*`, `.badge-*`, `.card`, `.data-table` with `data-label` mobile records, `.dialog-backdrop`, `.steps`, `.checklist`, …) ported from the approved `ui-prototype/`. Add classes there rather than inline styles
- Alpine.js 3.14 (pinned CDN, plus `@alpinejs/focus`) for dialogs, tabs, bulk selection and WebSocket components; shared `Alpine.data` components (`dialog`, `osTabs`, `bulkSelect`, `clipboard`, `mobileNav`, `dismissible`, `rowMenu`) and `punkHazard.wsUrl()` live in `static/js/punk-hazard.js`
- Templates: `templates/base.html` → `templates/layouts/{app,auth,project}.html`; reusable includes in `templates/partials/` (contracts + dialog convention documented in `templates/partials/README.md`); page-private fragments in `templates/<app>/includes/`. Django `{# #}` comments are single-line — use `{% comment %}` for blocks
- User-facing terminology: Test Runner (controller client), test machine, Visual engine (OmniParser, advanced diagnostics only), Application context (project prompt), Runs / Draft / Running / Passed, Import from TestRail, Connection key (API key)
- Onboarding wizard (`projects:create` → `setup_*` views) is not resumable and stores no wizard state; every step reads real project state
- No REST API — server-rendered HTML, data passed via template context

### Settings & Configuration

- All env vars read via `python-decouple` in `settings.py` — never import `decouple` directly elsewhere

## Parallel Development

This project uses git worktrees for parallel development. Each worktree must use a unique port when running the Django dev server to avoid conflicts (e.g., `runserver 8001`, `daphne -p 8001`).
