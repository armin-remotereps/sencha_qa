# agents/

**Verified desktop actions** (`agents/services/verified_element_actions.py`): `click`/`hover`/`drag` confirm the OmniParser candidate with the vision model before acting and (click always, hover/drag when `expected_result` is given) compare before/after screenshots afterwards, retrying up to 10 candidates per call and returning an error with the attempt history when none can be confirmed. The outcome check (`action_verifier.verify_action_outcome` → `OutcomeVerdict`) answers YES (`confirmed`), CHANGED (`unexpected`: intended element acted on, screen changed, expected result not shown) or NO (`missed`); only `missed` retries another candidate. `unexpected` stops at once and returns a non-error result (`format_unconfirmed_message`) saying the action was performed but NOT confirmed, with the vision reason, so the sub-agent re-observes and decides; clicking other candidates on an already-changed screen once clicked unrelated elements until the step timed out. After 3 rejected candidates on one screen parse (`MAX_CANDIDATE_REJECTIONS_PER_PARSE`) it raises `ElementNotFoundError` straight away instead of spending the rest of the budget on an element that is not on screen. Browser actions (`browser_click`/`browser_type`/`browser_hover`) check the element index exists before acting and reply `ELEMENT_NOT_FOUND` straight away, with Playwright actions capped at 10s so they finish before the server’s 30s reply timeout.

**Browser selection** (`agents/types.py::BrowserSelection`): a case runs its web steps in chromium (default), firefox, webkit, chrome or msedge. The agent picks one through the optional `browser` argument of `browser_navigate` only when the test case names a browser. `run_orchestrator` creates one mutable `BrowserSelection` per case and shares it with every sub-agent's `ToolContext`; every browser action sends `selection.current`, so the runner stays stateless. A runner without `browser_selection_v1`, or a browser not installed on the machine, raises `BrowserUnavailableError` and the case is Blocked (`browser_unavailable`).

**Double-click** (`double_click`, `browser_double_click`): desktop `double_click` runs the same verified flow as `click` through `tools_controller._verified_click` (click's messages are unchanged), with `default_double_click_expectation`. Both first call `ensure_runner_supports_double_click`; a runner without `double_click_v1` raises `RunnerOutdatedError` and the case is Blocked (`runner_outdated`).

**Closing apps** (`close_app(app_name, force?)`, `close_tab(app_name)`): housekeeping against leftover windows that clutter later OmniParser parses. The planner appends "Afterwards, close <App> with close_app ..." (or "close the <App> tab you opened with close_tab" for apps that also host the Test Runner's terminal or other needed tabs) to the last sub-task using the app; the sub-agent closes only after verifying the expected result and never fails a step over a close (`prompt_parts.build_app_lifecycle_rules`). Never the Test Runner or its terminal, the Playwright browser, or the app under test while in use. A runner without `close_app_v1` gets a tool error with a menu/key_press fallback, not a block. `force` is read as a strict JSON `true`. A Failed case, or a Blocked one whose machine still works (`projects/case_teardown_policy.py`), never reaches those clauses, so `projects.services._safe_teardown` runs `agents/services/case_teardown.py::run_case_teardown` in the case's `finally`, before `_safe_cleanup`: the close clauses of the steps without a passing final attempt (`case_teardown_prompts.pending_close_clauses`, matched by `orchestrator_prompts.CLOSE_CLAUSE_PREFIX`) plus the failed attempts' digests go to a sub-agent restricted to `TEARDOWN_TOOL_NAMES` (enforced by `allowlisted_dispatcher`; `build_sub_agent_system_prompt(tool_names=)` describes only those). No targets means no agent and no query. It records no attempt, writes no checkpoint, never changes the outcome and is capped by `CASE_TEARDOWN_TIMEOUT_SECONDS` (0 disables).

**Failed-attempt digest** (`agents/attempt_digest.py::build_attempt_digest`): every failed sub-agent result (timeout, max iterations, `RESULT: FAIL`) carries `SubTaskResult.actions_digest`, a deterministic list of its tool calls (compact args, result head) plus its last observation, capped at 6000 chars (head and tail kept). The evaluate prompt shows it, the recovery sub-agent gets it in its state, and after a passed recovery `_Progress.retry_notes` gives it to the retried step (so it does not repeat typed input or submits) while `state_lines` keep only a one-line `format_failed_attempt_state`. `_rebuild_state` rebuilds both on resume; the checkpoint stores the digest as an optional key. It never reaches the verdict, the case page or TestRail.

**Need help** (`orchestrator._pause_for_help`): after a failed step the evaluate prompt may answer `need_help` (environmental or transient obstacle, with `cause` and `help_ask`), and a `recover` that cannot go ahead (recovery failed, cap reached, no task) whose `cause` is not `product` escalates to it. The case stops without a verdict: cursor on the failed step, phase `awaiting_help`, `OrchestratorResult(status="need_help", help=HelpRequestInfo)` → `AgentStopReason.NEEDS_HUMAN_HELP` + `AgentResult.help`. `projects` writes the checkpoint `help` key when someone fixed the machine; with `continue_pending` the case skips `_restore_resumed_state` and re-runs the step, and the first checkpoint clears the flag. `_rebuild_state` anchors the help on the step's last failed attempt (failed-attempt line, `format_help_state_line` naming who fixed it (the setup agent, also when the help key's `auto_fix_fixed` is set and a person continued; a person; or a person after the setup agent could not) with the help key's `ask` (fallback: the need_help decision's reason), the setup agent's `auto_fix_summary` and the person's `note`, retry note with the digest); the verdict mentions the help. The executor fails fast on environmental obstacles with a SUMMARY starting `ENVIRONMENT:` (`prompt_parts.build_environment_obstacle_rules`). The orchestrator knows nothing of help modes or the ORM.

**Plan redesign during help** (`agents/plan_revision.py`): a help chat may replace the whole plan; `apply_plan_revision` (called by `projects` on Continue) writes the new `plan`, one synthetic passing `step` attempt with `carried_from=k` per carried new step (carried steps are a strictly increasing prefix; at least one step is not carried), `next_step = C+1`, `decisions = ()`, `plan_version + 1`, and moves the earlier plan's attempts and decisions into a `PlanRevisionRecord` (`plan_revisions`, newest 5). `attempts`/`decisions` therefore always describe the current plan, so step-number consumers need no filtering. `_Progress` carries `plan_version`/`plan_revisions` into every checkpoint (drop them and the first save after a resume loses the history). The help key keeps the earlier step N; `orchestrator_prompts.redesign_for_help` recognises the redesign by `plan_revisions[-1].help_request_id == help.request_id`. Then `_rebuild_state` writes the carried lines ("done before the plan was redesigned; earlier step k"), the redesign line and the help line labelled "Earlier plan, step N", and gives step C+1 the earlier failed attempt (with `paused_digest`) as its retry note; `_help_anchor_index` returns None. The resume starts at C+1 (also step 1) with no cleanup or restore while `continue_pending` is set. `format_attempt_lines` writes carried attempts as "PASSED under the earlier plan as step k …, not re-run", and the verdict adds the redesign sentence.
