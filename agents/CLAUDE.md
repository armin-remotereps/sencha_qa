# agents/

**Verified desktop actions** (`agents/services/verified_element_actions.py`): `click`/`hover`/`drag` confirm the OmniParser candidate with the vision model before acting and (click always, hover/drag when `expected_result` is given) compare before/after screenshots afterwards, retrying up to 10 candidates per call and returning an error with the attempt history when none can be confirmed. The outcome check (`action_verifier.verify_action_outcome` → `OutcomeVerdict`) answers YES (`confirmed`), CHANGED (`unexpected`: intended element acted on, screen changed, expected result not shown) or NO (`missed`); only `missed` retries another candidate. `unexpected` stops at once and returns a non-error result (`format_unconfirmed_message`) saying the action was performed but NOT confirmed, with the vision reason, so the sub-agent re-observes and decides; clicking other candidates on an already-changed screen once clicked unrelated elements until the step timed out. After 3 rejected candidates on one screen parse (`MAX_CANDIDATE_REJECTIONS_PER_PARSE`) it raises `ElementNotFoundError` straight away instead of spending the rest of the budget on an element that is not on screen. Browser actions (`browser_click`/`browser_type`/`browser_hover`) check the element index exists before acting and reply `ELEMENT_NOT_FOUND` straight away, with Playwright actions capped at 10s so they finish before the server’s 30s reply timeout.

**Browser selection** (`agents/types.py::BrowserSelection`): a case runs its web steps in chromium (default), firefox, webkit, chrome or msedge. The agent picks one through the optional `browser` argument of `browser_navigate` only when the test case names a browser. `run_orchestrator` creates one mutable `BrowserSelection` per case and shares it with every sub-agent's `ToolContext`; every browser action sends `selection.current`, so the runner stays stateless. A runner without `browser_selection_v1`, or a browser not installed on the machine, raises `BrowserUnavailableError` and the case asks for help (Need help, fault `browser_unavailable`); only a person marks a case Blocked.

**Double-click** (`double_click`, `browser_double_click`): desktop `double_click` runs the same verified flow as `click` through `tools_controller._verified_click` (click's messages are unchanged), with `default_double_click_expectation`. Both first call `ensure_runner_supports_double_click`; a runner without `double_click_v1` raises `RunnerOutdatedError` and the case asks for help (Need help, fault `runner_outdated`).

**Closing apps** (`close_app(app_name, force?)`, `close_tab(app_name)`): housekeeping against leftover windows that clutter later OmniParser parses. The planner appends "Afterwards, close <App> with close_app ..." (or "close the <App> tab you opened with close_tab" for apps that also host the Test Runner's terminal or other needed tabs) to the last sub-task using the app; the sub-agent closes only after verifying the expected result and never fails a step over a close (`prompt_parts.build_app_lifecycle_rules`). Never the Test Runner or its terminal, the Playwright browser, or the app under test while in use. A runner without `close_app_v1` gets a tool error with a menu/key_press fallback, not a block. `force` is read as a strict JSON `true`. A Failed case (`projects/case_teardown_policy.py`; only Failed gets a teardown) never reaches those clauses, so `projects.services._safe_teardown` runs `agents/services/case_teardown.py::run_case_teardown` in the case's `finally`, before `_safe_cleanup`: the close clauses of the steps without a passing final attempt (`case_teardown_prompts.pending_close_clauses`, matched by `orchestrator_prompts.CLOSE_CLAUSE_PREFIX`) plus the failed attempts' digests go to a sub-agent restricted to `TEARDOWN_TOOL_NAMES` (enforced by `allowlisted_dispatcher`; `build_sub_agent_system_prompt(tool_names=)` describes only those). No targets means no agent and no query. It records no attempt, writes no checkpoint, never changes the outcome and is capped by `CASE_TEARDOWN_TIMEOUT_SECONDS` (0 disables).

**Failed-attempt digest** (`agents/attempt_digest.py::build_attempt_digest`): every failed sub-agent result (timeout, max iterations, `RESULT: FAIL`) carries `SubTaskResult.actions_digest`, a deterministic list of its tool calls (compact args, result head) plus its last observation, capped at 6000 chars (head and tail kept). The evaluate prompt shows it, the recovery sub-agent gets it in its state, and after a passed recovery `_Progress.retry_notes` gives it to the retried step (so it does not repeat typed input or submits) while `state_lines` keep only a one-line `format_failed_attempt_state`. `_rebuild_state` rebuilds both on resume; the checkpoint stores the digest as an optional key. It never reaches the verdict, the case page or TestRail.

**Need help** (`orchestrator._pause_for_help`): after a failed step the evaluate prompt may answer `need_help` (environmental or transient obstacle, with `cause` and `help_ask`), and a `recover` that cannot go ahead (recovery failed, cap reached, no task) whose `cause` is not `product` escalates to it. The case stops without a verdict: cursor on the failed step, phase `awaiting_help`, `OrchestratorResult(status="need_help", help=HelpRequestInfo)` → `AgentStopReason.NEEDS_HUMAN_HELP` + `AgentResult.help`. `projects` writes the checkpoint `help` key when someone fixed the machine; with `continue_pending` the case skips `_restore_resumed_state` and re-runs the step, and the first checkpoint clears the flag. `_rebuild_state` anchors the help on the step's last failed attempt (failed-attempt line, `format_help_state_line` naming who fixed it (the setup agent, also when the help key's `auto_fix_fixed` is set and a person continued; a person; or a person after the setup agent could not) with the help key's `ask` (fallback: the need_help decision's reason), the setup agent's `auto_fix_summary` and the person's `note`, retry note with the digest); the verdict mentions the help. Infrastructure faults (runner lost or unresponsive, visual engine, AI service, time limit, browser unavailable, runner outdated, resume state lost, internal error) never block a case: `projects` opens a Need help request at the checkpoint's `next_step` (clamped to the last step for a fault during the verdict) with `CheckpointHelp.fault` (the fault's label). Such a step may have been interrupted before any attempt was recorded, so when `_help_anchor_index` finds no failed attempt (and the help made no redesign) `_rebuild_state` puts the help line just before that step's first attempt, or last (`_interrupted_by_fault`); the help line, the verdict note (`help_verdict_note`) and `_applied_help` name the fault. How Continue goes on is `projects.models.HelpContinueMode`, decided at pause time by `projects.case_faults.help_continue_mode`: `current_screen` (help key with `continue_pending`), `restore` (help key without it: cleanup and restore sub-task, then the step; runner faults or any fault before a due restore finished: `restore_baseline` in `projects.services.execute_test_run_test_case`) or `from_scratch` (checkpoint cleared, no help key). The executor fails fast on environmental obstacles with a SUMMARY starting `ENVIRONMENT:` (`prompt_parts.build_environment_obstacle_rules`). The orchestrator knows nothing of help modes or the ORM. A person's pause (`projects` case pause) stops the case at the next `_check_cancelled` (also checked just before the verdict phase) and its help key carries `CheckpointHelp.paused_by` (the pauser's server label): `_interrupted_by_fault` / `_applied_help` treat it like a fault, and `format_help_state_line` / `help_verdict_note` say the step was paused and discussed and may be partly done.

**Plan redesign during help** (`agents/plan_revision.py`): a help chat may replace the whole plan; `apply_plan_revision` (called by `projects` on Continue) writes the new `plan`, one synthetic passing `step` attempt with `carried_from=k` per carried new step (carried steps are a strictly increasing prefix; at least one step is not carried), `next_step = C+1`, `decisions = ()`, `plan_version + 1`, and moves the earlier plan's attempts and decisions into a `PlanRevisionRecord` (`plan_revisions`, newest 5). `attempts`/`decisions` therefore always describe the current plan, so step-number consumers need no filtering. `_Progress` carries `plan_version`/`plan_revisions` into every checkpoint (drop them and the first save after a resume loses the history). The help key keeps the earlier step N; `orchestrator_prompts.redesign_for_help` recognises the redesign by `plan_revisions[-1].help_request_id == help.request_id`. Then `_rebuild_state` writes the carried lines ("done before the plan was redesigned; earlier step k"), the redesign line and the help line labelled "Earlier plan, step N", and gives step C+1 the earlier failed attempt (with `paused_digest`) as its retry note; `_help_anchor_index` returns None. The resume starts at C+1 (also step 1) with no cleanup or restore while `continue_pending` is set. `format_attempt_lines` writes carried attempts as "PASSED under the earlier plan as step k …, not re-run", and the verdict adds the redesign sentence.

**Plan redesign after a result review** (`PlanRevisionRecord.source="review"`, `help_request_id=None`): the result chat may redesign a finished case's plan and re-run it. `apply_plan_revision(source="review")` clears `help`, sets phase `step` and records the last failed step (with its digest) as `paused_step`. `redesign_for_help` matches only `source="help"` records; `orchestrator_prompts.redesign_for_review` matches the newest record when it is a review one. `_rebuild_state` then writes the carried lines, `format_review_redesign_state_line` ("redesigned after a person reviewed the earlier result ... continue at step C+1", or "runs again from step 1" when nothing was carried) and gives step C+1 the earlier failed attempt as its retry note only when the record kept a digest. Unlike a help redesign the resume is a normal one (no help key, so no `continue_pending`): cleanup, then the restore sub-task when 1 < `next_step` <= len(plan). The verdict always names a review redesign (also with C = 0) and says the carried steps' state was restored. A later help in the same execution anchors on the new step numbers as usual.

**Final turn on timeout** (`AgentConfig.final_answer`, `FinalAnswerPolicy`): when a sub-agent's budget runs out, `agent_loop.run_tool_loop` asks once more with `tool_choice="none"` (prompt `sub_agent_prompts.build_final_answer_prompt`, call capped by `AGENT_FINAL_ANSWER_TIMEOUT_SECONDS`, 0 disables). Only the orchestrator's step, recovery and restore sub-agents opt in; teardown and machine setup keep `None`. The stop reason stays `TIMEOUT` with `AgentResult.answered_after_timeout`; `sub_agent._parse_sub_task_result` turns an explicit `RESULT: PASS` there into a normal pass whose summary ends "(answered when the step's time budget ran out)". A failed or empty final call ends the step exactly as before.

**`click_at` and `scroll`** (`tools_controller`): `click_at(x, y, expected_result?)` sends the existing `click` message with screenshot-pixel coordinates (works on every runner) and, only with `expected_result`, runs one before/after outcome check with no retry. `scroll(direction, amount, x?, y?)` needs `scroll_v1`; without it the tool returns an error suggesting key presses. `take_screenshot` tells the vision model the image size so the coordinates it reports are the ones these tools take. Command output from `execute_command`/`wait_for_command`/`send_command_input` goes through `agents/command_output.clean_command_output` (ANSI codes, carriage-return progress lines, runs of identical lines) before the result cap.

**Person steps (Human in the loop)** (`agents/services/person_steps.py`, prompts in `person_step_prompts.py`): `run_orchestrator(person_mode=)` takes a callable asked at each step boundary (projects reads `TestRun.help_mode == "hitl"`); while it answers True the step is not run by a sub-agent. `prepare_person_step` (one tool-free LLM call, JSON validated; any unusable answer falls back to the plan step text, executor vocabulary stripped, as `interactive`) writes a `PersonStepHandOff`; `kind="command"` only when the case text states that exact command as a whole (`_is_explicit_command`, checked in code: whitespace-collapsed it equals a full line, optionally after a list marker or `$ `/`> ` prompt, or a full inline-code span or quoted string; a fragment such as "rm -rf build" of "rm -rf build && make" fails). The orchestrator stores it in the checkpoint `person` key (`state="waiting"`, `requested_at`), sets phase `awaiting_person` and returns `OrchestratorResult(status="awaiting_person")` → `AgentStopReason.AWAITING_PERSON` + `AgentResult.person_step`; a re-entry that finds the same step `waiting` re-uses the stored hand-off. `projects` writes the report (`reported`), the overrule (`overruled`) or the mode-switch hand-back (`handed_back`), each with `continue_pending` (no cleanup, no restore; cleared by the first checkpoint). On re-entry: `reported` runs `confirm_person_step`, a sub-agent restricted to `CONFIRM_TOOL_NAMES` (`take_screenshot`, `execute_command`, `wait_for_command`; read-only checks by prompt; the step text (instruction, expected result, command: TestRail-derived) and the report are each fenced as data with markers `_fence` strips from the content, budget `PERSON_STEP_CONFIRM_TIMEOUT_SECONDS`, no final-answer turn). "As expected" + PASS records a `step` attempt with `performed_by="person"`, `person_step_id=request_id` and duration `reported_at - requested_at`; FAIL re-hands the step with `objection` and records nothing (the person decides). `_hand_off_to_person` asks `person_mode()` again right before every hand-off (after prepare, after a failed confirmation): when it is off the person key is dropped and the agent runs the step (or the restore) from the current screen, with no cleanup or restore. "Different" records a fail attempt with the person's note (quoted and labelled as their words, not instructions) and the agent's observation; then `_evaluate_person_failure` (own system+user call, prompts `build_person_failure_*`) asks whether a remaining step depends on it: `continue` (FAILED line, cursor + 1, checkpoint, next hand-off) or `stop` (also for an unparseable answer; the last step records `continue` without a call). At the verdict, when every failed final step is such a continued person failure (`_judged_person_failures`), `_judge_person_failures` lets the LLM decide pass or fail (`build_person_failure_verdict_prompt`, JSON `{result, summary}`; pass only on an explicit "pass" with a summary, any AI fault fails); otherwise pass/fail stays deterministic. `overruled` records a pass whose summary starts `OVERRULE_SUMMARY_PREFIX`, without a check. `handed_back` (or `waiting` once the mode is off) runs the step normally; with the mode on again it is a fresh hand-off. A due restore after a resume is handed out the same way (`kind="restore"`, recorded as a `resume` attempt; "different" raises `ResumeStateLostError`); a restore key whose `step_num` is not the cursor's `next_step` is stale and dropped. No `_evaluate_failure`, recovery or need_help on person steps; faults in prepare/confirm raise as for any step. `format_attempt_lines` labels person attempts and the verdict prompt says who performed what. **How to do it** (`PersonStepHandOff.how_to`, `PersonHowToItem(text, command)`): the prepare prompt also asks for 1–8 numbered, OS-specific items (how to open the app, `agents/os_shell.open_shell_hint` — on Windows Command Prompt only, never PowerShell/Windows Terminal — a one-line minimal command in `shell_syntax_hint` syntax, and what right and wrong output look like) for shell/OS/env/file/version/install steps and non-obvious UI paths. These commands are AI *suggestions*, never checked with `_is_explicit_command` (that stays the rule for `kind="command"` only); `_parse_how_to` drops bad items (not objects, empty text, multi-line or > 500-char command; text stripped of executor vocabulary, ≤ 400; ≤ 8 items) and never discards the hand-off for them; the fallback has none. The confirm sub-task lists suggested commands inside the fenced step and judges any step with a command (stated or suggested) by its pasted output first. `format_how_to_text` is the numbered plain-text form (old-runner fallback). **Ask AI** (`agents/services/person_step_advisor.answer_person_step_question`, prompts in `person_step_advice_prompts.py`): one tool-free LLM call over a `PersonStepAdviceContext` (case text, application context, hand-off, earlier Q&A, all fenced as data); it only explains, never claims to have seen the machine, never tells the person to pass, skip or mark the step; answer capped at 4000; an `AIServiceError` (also for an empty answer) propagates.

**Case step references** (`agents/case_step_refs.py`): `run_orchestrator(case_step_count=, case_steps_testrail=)` — with a count > 0 the plan prompt asks for `case_steps` per sub-task (prompt unchanged at 0); `_build_sub_task` normalizes them (1..N, unique, sorted, ≤ 50; bad values dropped, never an error), recoveries get none. `_Progress` carries `case_step_count` / `case_steps_testrail` into every checkpoint (a resume takes them from the checkpoint when it has a count). `prepare_person_step` copies the step's refs onto the hand-off, never for a restore. `validate_plan_revision` normalizes sent refs against the checkpoint's count; a carried step sent without refs keeps the earlier step's; `plan_fingerprint` ignores them.
