# 013. Inline OmniParser into Controller Client — Implementation

Spec: [`docs/specs/013.Inline OmniParser into Controller Client.md`](../specs/013.Inline%20OmniParser%20into%20Controller%20Client.md)

## Summary

OmniParser screen-parsing moved from a centrally-hosted FastAPI/GPU service (`omniparser_service/`) into `controller_client`, the standalone Python client end users run on their own machine. The controller now takes its own screenshot and runs OmniParser locally in-process (device auto-detected: `cuda` → `mps` → `cpu`) in response to a single new WebSocket action, `find_element`, replying with the full parsed result in one round trip. The central service, the root vendored `OmniParser/` copy, and all `OMNIPARSER_URL`/`OMNIPARSER_API_KEY` HTTP-client plumbing are removed entirely.

## What was built

- **Controller client**: vendored OmniParser's `util/` package into `controller_client/omniparser/util/`; added `controller_client/omniparser_config.py` (env-driven thresholds/weights-dir) and `controller_client/omniparser_executor.py` (device detection, a lazy-loaded singleton model wrapper, `execute_find_element()`); wired a new `find_element`/`find_element_result` message pair into `controller_client/protocol.py` and `controller_client/client.py`.
- **Packaging**: `controller_client/requirements.txt` gained the full OmniParser dependency stack; `setup.sh`/`.ps1`/`.bat` install a platform-appropriate `torch` build (CUDA on Linux/Windows with an NVIDIA GPU, CPU-only otherwise, standard wheel on macOS) and download the ~1.5GB model weights during setup.
- **Server side**: `projects/services.py` gained `controller_find_elements()`, dispatching the new action over the existing channel-layer pattern; matching plumbing added to `projects/controller_protocol.py`, `projects/controller_consumer.py`, `projects/controller_reply_tracker.py`. `agents/services/controller_element_finder.py` and `agents/services/controller_omniparser_element_finder.py` merged into one file with a single code path (no more `is_omniparser_configured()` branch, no more vision-LLM-guess fallback); `agents/services/omniparser_client.py` deleted.
- **Cleanup**: `omniparser_service/`, the root `OmniParser/` directory, `scripts/download_omniparser_weights.sh`, and the `OMNIPARSER_*` Django settings are all removed. `CLAUDE.md` and `.pre-commit-config.yaml` updated to match (both had stale references to the deleted service caught during review).

## Environment actually exercised

This development machine is a Mac (Apple Silicon), so setup exercised the **MPS** branch: `torch.backends.mps.is_available()` → `True`, `torch.cuda.is_available()` → `False`. The `.ps1`/`.bat` platform-aware install paths were written to mirror `setup.sh`'s logic exactly but could not be executed here (Windows-only).

## Real issues found and fixed while actually running this

Running the real setup and a manual connectivity check surfaced several genuine bugs beyond what the plan anticipated:

1. **`download_omniparser_weights.sh` called a bare `hf` binary** that isn't on `PATH` outside the venv — it silently failed immediately with "command not found," which looked like a multi-hour stall from the outside (a stray `tail -f` was left watching a dead log). Fixed to resolve the venv's own `hf` binary directly, with a bare-`hf` fallback.
2. **mypy `unused-ignore` inconsistency**: one of three structurally-identical deferred `type: ignore[import-not-found]` comments (for the `util.*` imports that only resolve after `sys.path` is mutated at runtime) was flagged "unused" by mypy in this environment, while the other two weren't. Widened all three to `# type: ignore[import-not-found, unused-ignore]`, mypy's documented mechanism for an ignore whose necessity is environment-dependent.
3. **mypy config gaps**: `controller_client/setup.cfg`'s exclude only covered `omniparser/util`, not `omniparser/weights` (which bundles a `handler.py` from the downloaded Hugging Face repo itself) — widened to `omniparser/(util|weights)`. A missing `pexpect` stub was initially "fixed" with `ignore_missing_imports` (wrong — the root project's own `setup.cfg`/`requirements.txt` already solves this correctly with a `types-pexpect` stub package); corrected during review to match. The root project's own `setup.cfg` was also missing an exclusion for `controller_client` entirely (which has its own separate venv/dependencies, including `torch`) — without it, `mypy .` at the repo root broke on missing `torch`.
4. **`_OmniParserModel._load()` didn't fail fast on a missing weights directory**: found during manual connectivity testing — a bad `OMNIPARSER_WEIGHTS_DIR` doesn't produce an immediate error; the vendored YOLO loader treats an unrecognized local path as a Hugging Face Hub model ID and silently starts downloading it instead. Fixed by checking the expected weight files exist before constructing `Omniparser(config)`, raising a clear `ExecutionError` otherwise.
5. Two now-empty leftover directories (`OmniParser/`, `OmniParser/util/`) were left on disk after moving the vendored files out in an earlier step — invisible to git (which doesn't track empty directories) but present in the working tree; removed manually.

## Testing

Partway through implementation, the project's testing convention changed from E2E-agent-only to unit tests (see `.claude/CLAUDE.md`, `.claude/rules/testing-constraits.md`, `.claude/rules/task-implementation-flow.md`, updated accordingly). A partial E2E logic check ran before that switch and confirmed the WebSocket handshake and dispatch/timeout/error-handling path work correctly; it also surfaced the weights fail-fast bug (#4 above) before being stopped in favor of the new convention.

Unit test coverage added:
- `controller_client/tests/test_protocol.py` — `find_element` payload parsing, serialization round-trip.
- `controller_client/tests/test_omniparser_executor.py` — pixel-coordinate scaling, draw-config scaling, device detection, and the weights fail-fast check.
- `projects/tests/test_controller_find_elements.py` — `controller_find_elements()`'s success/failure paths and `_build_pixel_element()`'s field mapping, with the channel-layer dispatch mocked.
- `agents/tests/test_controller_element_finder.py` — `find_element_coordinates()`'s empty-result/happy-path behavior and its LLM-matching helpers, with the controller dispatch and LLM call mocked.

Final verification, all green: root `mypy .` (90 files), `controller_client` mypy (21 files, its own separate strict config), `python manage.py check`, `python manage.py test agents.tests projects.tests` (11 tests), `controller_client/.venv/bin/python -m pytest controller_client/tests/` (10 tests).
