# Verified click / hover / drag: pre-action candidate check + post-action confirmation loop (max 10 attempts)

## Context

The OmniParser-based desktop tools (`click`, `hover`, `drag` in `agents/services/tools_controller.py`) resolve a natural-language
description to screen coordinates through one LLM call (`find_element_coordinates` → `_match_element_by_description` in
`agents/services/controller_element_finder.py`) and then act immediately. When the matcher picks the wrong numbered box the
tool still reports `Clicked element at (x, y): <description>` and the agent believes it succeeded. The bug report asks for a
verification loop, capped at 10 iterations, that checks whether the *asked-for* item was actually acted on.

Decisions taken with the user:
- Each attempt = **pre-action verify** (vision model confirms the highlighted candidate is the described element) → act →
  **post-action confirm** (vision model compares before/after screenshots against the intended outcome).
- Tools gain an optional `expected_result` argument that drives the post-action question; without it, `click` falls back to a
  generic "did the click land on '<description>' / did the UI react" question. For `hover` and `drag` post-action confirmation
  runs only when `expected_result` is supplied (a generic "did the UI react" question is unreliable for hover).
- Applies to `click`, `hover`, `drag` (all three share the OmniParser path). `browser_click` unchanged.
- Cap is a hard-coded constant `MAX_VERIFY_ATTEMPTS = 10` (no new env var).

## Design

### Attempt accounting
One shared counter per tool call. Every candidate evaluation consumes one attempt, whether it fails at the pre-action check
or at the post-action check. When the counter hits 10 the tool returns an error result listing what was tried. The loop also
stops early when `ToolContext.deadline` (already computed by `agent_loop.py:178`) has fewer than a few seconds left or
`cancellation_check` fires, so a slow OmniParser cannot blow the sub-agent timeout ten times over.

### Excluding rejected candidates
- Inside one OmniParser parse: exclude by element **index** (rejected indices are removed from the list handed to the matcher).
- Across parses (screen may have changed after a wrong click): indices are not stable, so exclude by **center position**
  (`abs(dx) <= 10 and abs(dy) <= 10` px against every rejected center). Both exclusions are applied together.
- If exclusion leaves zero elements → `ElementNotFoundError` (existing exception), surfaced by `safe_tool_call`.

### Per-attempt flow (`click`)
1. `controller_find_elements` → `PixelParseResult` (publish annotated image via `on_screenshot(..., "controller_omniparser")`, as today).
2. Match with existing prompt (`_match_element_by_description`) over the filtered element tuple.
3. **Pre-action verify**: one vision call with the annotated image + the candidate's list line:
   "Box [N] (content=…) was selected as '<description>'. Is box N really that element? Reply YES or NO, then one short reason."
   NO → record rejection (index + center + reason), count attempt, go to 1 (re-use the same parse if the screen was not touched:
   skip step 1 while no action has been performed since the last parse).
4. `before = controller_screenshot`; `controller_click(x, y)`; `_ensure_action_succeeded`; `time.sleep(POST_ACTION_SETTLE_SECONDS = 1.0)`;
   `after = controller_screenshot` (publish via `on_screenshot(after, "click")`).
5. **Post-action confirm**: one vision call with both images:
   "The agent clicked '<description>' at (x, y). Expected result: <expected_result or generic fallback>. Comparing before and
   after, did the click hit the intended element and produce that result? Reply YES or NO, then one short reason."
   YES → success. NO → record rejection (center + reason), count attempt, go to 1 (fresh parse, screen changed).
6. Success content: `Clicked element at (x, y): <description> (verified on attempt K)`; when K > 1 append one line per rejected
   candidate so the agent sees what was skipped. Failure after 10: `click error: could not verify a click on '<description>'
   after 10 attempts: <one line per attempt>` (`is_error=True`).

### `hover`
Same loop; post-action confirm only when `expected_result` is given, otherwise the tool succeeds once the pre-action verify passes.

### `drag`
Resolve **start** then **end** through the shared pre-action verify (same attempt counter), perform the drag, post-action
confirm only when `expected_result` is given. On a post-action NO both descriptions are re-resolved on the next attempt.

## Files

### New: `agents/services/action_verifier.py`
Vision-only helpers, no controller calls:
- `verify_candidate(vision_config, parse_result, candidate, description) -> Verdict`
- `verify_action_outcome(vision_config, before_b64, after_b64, action_summary, expected_result) -> Verdict`
- `_parse_verdict(text) -> Verdict` (YES/NO prefix + reason; unparseable → treated as NO with the raw text as reason).
Reuses `send_chat_completion`, `ChatMessage`, `ImageContent`, `TextContent` exactly like `vision_qa.py`.

### New: `agents/services/verified_element_actions.py`
The loop. Public surface:
- `MAX_VERIFY_ATTEMPTS = 10`, `POST_ACTION_SETTLE_SECONDS = 1.0`
- `resolve_verified_element(project_id, description, vision_config, budget, *, on_screenshot) -> PixelUIElement`
  (parse → filtered match → pre-verify; loops until accepted or budget exhausted; keeps `RejectedCandidate` records on the budget).
- `confirm_action(project_id, vision_config, budget, before_b64, action_summary, expected_result, *, on_screenshot, tool_name) -> Verdict`
  (settle, after-screenshot, post-verify, record rejection on NO).
- `VerificationBudget` (mutable dataclass: `max_attempts`, `used`, `rejections: list[RejectedCandidate]`, `deadline`, `cancellation_check`;
  `consume()` raises `ActionVerificationError` with the full history when exhausted or out of time; `is_rejected(element) -> bool`).
- `ActionVerificationError(Exception)` → add to `agents/exceptions.py` next to `ElementNotFoundError`.

### Modified: `agents/services/controller_element_finder.py`
Split `find_element_coordinates` into reusable pieces without changing prompts:
- `parse_screen(project_id, *, on_screenshot) -> PixelParseResult` (the `controller_find_elements` + publish + empty check).
- `match_element(parse_result, description, vision_config, *, excluded: Callable[[PixelUIElement], bool]) -> PixelUIElement`
  (wraps `_match_element_by_description` over the filtered tuple; raises `ElementNotFoundError` when nothing is left).
- Keep `find_element_coordinates` as a thin composition of the two (still exported from `agents/services/__init__.py`, still
  covered by `agents/tests/test_controller_element_finder.py`).

### Modified: `agents/services/tools_controller.py`
`click`, `hover`, `drag` take `expected_result: str = ""`, `cancellation_check`, `deadline` and delegate to the new loop.
`_ensure_action_succeeded` stays as is. No other tool changes.

### Modified: `agents/services/tool_registry.py`
`_handle_click`, `_handle_hover`, `_handle_drag` read the optional `expected_result` argument and pass
`context.cancellation_check` / `context.deadline` (same pattern as `_handle_wait` at line ~266).

### Modified: `agents/services/tool_definitions.py`
Add optional `expected_result` `ToolParameter` to `click`, `hover`, `drag`; extend the three descriptions to say the tool verifies
the target before and after acting and retries automatically.

### Modified: `agents/services/prompt_parts.py`
`build_desktop_tool_examples`: show `click(description="the Login button", expected_result="the login form opens")`, and one
line telling the agent that click/hover/drag self-verify (up to 10 candidates) and that a returned error means the element could
not be confirmed, so it should re-describe the element or take a screenshot rather than blindly retrying.

### Modified: `agents/types.py`
`Verdict(accepted: bool, reason: str)` and `RejectedCandidate(index, center_x, center_y, content, stage: Literal["candidate", "outcome"], reason)`
as frozen dataclasses.

### Docs
No spec file exists for this bug; after the user's final confirmation write `docs/impl/<next-number>.verified-click-impl.md`
describing the loop, and add a short "Verified desktop actions" line to `.claude/CLAUDE.md` under AI Agent Loop.

## Verification

Unit tests (`SimpleTestCase`, all controller/LLM calls patched — same style as `agents/tests/test_tools_controller.py`):
- `agents/tests/test_action_verifier.py`: YES/NO/garbage verdict parsing; prompts include description, expected_result, both images.
- `agents/tests/test_verified_element_actions.py`:
  - candidate rejected at pre-verify → next match receives the filtered element list (index exclusion), one attempt consumed;
  - candidate rejected at post-verify → re-parse happens and the near-identical center is excluded next time (position exclusion);
  - exactly 10 attempts then `ActionVerificationError` with the history; controller never clicked more than the confirmed count;
  - deadline nearly reached / cancellation → stops before 10;
  - success on attempt 1 → single click, before/after screenshots taken, `on_screenshot` called for the after image.
- `agents/tests/test_tools_controller.py`: update `ClickToolTests` (patch the new loop), add hover-without-expected_result
  skips post-confirm, drag resolves two elements and confirms only when expected_result given, blocked-input error still surfaces.
- `agents/tests/test_controller_element_finder.py`: keep green; add `match_element` exclusion test.
