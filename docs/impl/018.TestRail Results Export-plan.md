# 018. Push run results to TestRail — Implementation Plan

## Context

017 made TestRail a read-only source (`projects/testrail_client.py` has GET methods only; the Settings card even promises "Punk Hazard never writes to TestRail"). The user now wants the reverse direction: after a run finishes, one button pushes its case results to TestRail over the API. Pushing again only sends results that changed since the last push; unchanged ones are skipped.

TestRail fact that shapes the design: results are **append-only** (`add_results_for_cases`; there is no update-result endpoint). "Update if changed" therefore means *append a new result* for that case, and "ignore" means *skip* a case whose status and comment match what we pushed last time. We record what was pushed per case to make that comparison.

Decisions taken with the user (AskUserQuestion, 2026-09-17):

| Question | Decision |
|---|---|
| Push unit / location | Per run. "Push to TestRail" button on the Run detail page, shown for finished (done/cancelled) runs. |
| Target TestRail run | Auto-create one TestRail run per Punk Hazard run on first push; store its id on `TestRun`, reuse on later pushes. User picks TestRail project (+ suite for multi-suite) in a dialog on first push, preselected from the cases' import history. |
| Payload | `success`→Passed(1), `failed`→Failed(5). Cancelled / not started / running pivots are skipped. Comment = agent result text + link back to the case detail page. `elapsed` from started/finished timestamps. No screenshots. |
| Execution | Celery task on the `upload` queue; run page shows Pushing / Pushed at … / Failed with the TestRail message. |

## Verified TestRail API v2 facts used here

- `POST add_run/{project_id}` body `{suite_id, name, description, include_all: false, case_ids: [...]}` → run object with `id`, `is_completed`, `url`. `suite_id` required for multi-suite projects, accepted for single-suite ones (we always send it).
- `GET get_run/{run_id}` → run object (`is_completed`); `400/404` when deleted.
- `POST update_run/{run_id}` body `{include_all: false, case_ids: [...]}` replaces the run's case set (so we send the full set every time).
- `POST add_results_for_cases/{run_id}` body `{results: [{case_id, status_id, comment, elapsed}]}` → list of result objects (each with `id`, `status_id`, `test_id`) in the same order. Results are immutable; each call appends.
- `elapsed` is a timespan like `"1h 2m 3s"`, must be ≥ 1s; omit the key when unknown/zero.
- Built-in status ids: 1 Passed, 5 Failed. Same auth, 429/`Retry-After`, error envelope as the GETs.
- Result comments are TestRail markdown. Run URL: `{testrail_url}/index.php?/runs/view/{run_id}`.

## Client: write methods on `TestRailClient` (`projects/testrail_client.py`)

- Drop the "read-only by construction" docstring; generalize `_request_with_rate_limit_retry(method, json_body: dict | None)` so GET and POST share the 429/`Retry-After`, network-error and error-envelope handling. Add `_post_json(method, body)` next to `_get_json`.
- New dataclasses: `TestRailRun(id, name, is_completed, url)`, `TestRailResultInput(case_id, status_id, comment, elapsed)` (`elapsed=""` → key omitted), `TestRailResult(id, status_id)`.
- New methods: `get_run(run_id)`, `add_run(project_id, *, suite_id, name, description, case_ids)`, `update_run(run_id, *, case_ids)`, `add_results_for_cases(run_id, results) -> list[TestRailResult]`. `add_results_for_cases` raises `TestRailError` if the response list length differs from the request (we rely on positional order).

## Pure mapping (`projects/testrail_mapping.py` additions, no ORM)

- `TESTRAIL_STATUS_PASSED = 1`, `TESTRAIL_STATUS_FAILED = 5`; `map_pivot_status_to_testrail(status: str) -> int | None` (`success`→1, `failed`→5, else `None` = not pushable).
- `parse_testrail_case_id(raw: str) -> int | None` — accepts `"123"` and `"C123"` (XML exports store the `C` prefix, API imports store bare digits); anything else → `None`.
- `format_testrail_elapsed(started_at, finished_at) -> str` — `"1h 2m 3s"` style, `""` when either is missing or the span is under 1s.
- `build_result_comment(*, outcome_label, run_name, result_text, case_url) -> str` — markdown: first line `"{Passed|Failed} by Punk Hazard in run “{run_name}”."`, blank line, result text truncated to 4000 chars, blank line, `"Details: {case_url}"`.
- `comment_hash(comment: str) -> str` (sha256 hex).

## Services: new module `projects/testrail_results_services.py`

Reuses from `projects/testrail_services.py`: `build_testrail_client`, `TestRailNotConfiguredError`, `get_testrail_picker_state`, `resolve_testrail_import` / `resolve_testrail_import_suite` / `TestRailImportTarget` (already generic "TestRail project + suite" resolution — reused as-is, no rename, to keep this change incremental).

Dataclasses:
- `PlannedResult(pivot, case_id, status_id, comment, elapsed)`.
- `TestRailPushPlan(results: list[PlannedResult], changed: list[PlannedResult], skipped_no_case_id: int, skipped_not_pushable: int)`.
- `TestRailPushOutcome(pushed, unchanged, skipped_no_case_id, testrail_run_id)`.
- `TestRailPushPanel(configured, has_target, picker: TestRailPickerState | None, suggested_project_id: int | None, pending_count, run_url)` — everything the Run detail template needs.

Functions:
- `plan_testrail_push(test_run, *, links_base_url) -> TestRailPushPlan`: one query over `pivot_entries.select_related("test_case")`; per pivot map status, parse case id, build comment (case URL = `links_base_url` + `reverse("projects:test_run_case_detail", ...)`), mark `changed` when `testrail_pushed_status_id != status_id or testrail_pushed_comment_hash != comment_hash(comment)`.
- `suggest_testrail_target(test_run) -> tuple[int | None, int | None]`: most common `(upload.testrail_project_id, upload.testrail_suite_id)` among the run's cases' uploads (API imports only); `(None, None)` otherwise.
- `get_testrail_push_panel(test_run, *, links_base_url) -> TestRailPushPanel`: only calls the picker (cached 5 min) when the run is finished, settings exist and the run has no target yet.
- `can_push_testrail_results(test_run) -> bool`: status in (DONE, CANCELLED) and push status != PUSHING.
- `set_testrail_target(test_run, target: TestRailImportTarget) -> None`.
- `start_testrail_results_push(*, test_run, links_base_url) -> None`: validates (`ValueError` for wrong run state / already pushing, `TestRailNotConfiguredError`, `ValueError` "choose a TestRail project first" when no target), sets `PUSHING`, blanks error, saves, broadcasts, `celery_app.send_task("projects.tasks.push_test_run_results", args=[test_run.id, links_base_url])` (same `send_task` pattern as 017 to avoid the services→tasks cycle).
- `push_test_run_results(test_run, *, links_base_url) -> TestRailPushOutcome` (called by the task):
  1. `plan = plan_testrail_push(...)`.
  2. `case_ids` = case ids of every planned result ∪ case ids of pivots that already have `testrail_result_id` (keeps previously pushed cases in the run).
  3. `_ensure_testrail_run`: no `testrail_run_id` → `add_run` (name `"Punk Hazard: {run.display_name}"`, description with project name + run link) and store the id. Existing id → `get_run`; if it raises 400/404 or `is_completed`, create a fresh run, store it, and null the pivot tracking for this run (so everything is pushed again); otherwise `update_run(case_ids)`.
  4. For `plan.changed` in batches of 100: `add_results_for_cases`, then `bulk_update` the pivots' four tracking fields (inside `transaction.atomic()` per batch).
  5. Return outcome; caller stamps run fields.
- `mark_testrail_push_succeeded(test_run, outcome)` / `mark_testrail_push_failed(test_run, message)`: set status, `pushed_at`, summary/error, save, broadcast.
- `build_testrail_run_url(project, run_id) -> str`.
- Broadcast: `_broadcast_testrail_push(test_run)` sends `{"type": "test_run.testrail_push", "push_status": ...}` to the existing `test_run_{id}` group (helper `_test_run_group` lives in `projects/services.py`; import it).

## Celery task (`projects/tasks.py`)

`push_test_run_results(self, test_run_id: int, links_base_url: str)` — `queue="upload"`, `max_retries=0`, `acks_late`, `reject_on_worker_lost`, `soft_time_limit=600`, `time_limit=660`, registered in `settings.CELERY_TASK_ROUTES` (the existing `test_celery_task_routes.py` enforces this). Body mirrors `import_testrail_cases`: fetch run or log+return; try `push_test_run_results` → `mark_testrail_push_succeeded`; `TestRailError`/`TestRailNotConfiguredError` → `mark_testrail_push_failed(exc.message)`; other exceptions → `logger.exception` + generic message.
