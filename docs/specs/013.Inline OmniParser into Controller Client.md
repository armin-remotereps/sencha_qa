# 013. Inline OmniParser into Controller Client

## Background

OmniParser is used to reliably locate UI elements on screen for native `click`/`hover`/`drag` actions during AI-driven test execution. Today it runs as a standalone, GPU-hosted FastAPI service (`omniparser_service/`), reached over HTTP from the Django `agents` app (`agents/services/omniparser_client.py`). This requires operating a separate GPU deployment centrally, independent of the end user's own `controller_client` machine.

This refactor moves OmniParser out of the central service entirely and inlines it directly into `controller_client` — the standalone Python client end users download and run on their own machine. Screen parsing then happens locally, on the same machine that's already taking screenshots and executing actions, with no third-party/central service involved.

## Goals

- Every OmniParser request runs locally inside `controller_client`, on the end user's own machine.
- The central `omniparser_service` (FastAPI app + GPU Docker deployment) is retired entirely.
- OmniParser support is bundled by default in every `controller_client` install — no separate opt-in step.
- Works on any machine the client is installed on: CUDA GPU, Apple Silicon (MPS), or CPU-only, auto-detected.

## Non-Goals

- No change to `browser_click`/`browser_hover`/etc. — those already use Playwright element indices via `browser_get_elements` and never touched OmniParser.
- No change to the explicit `take_screenshot`/`browser_take_screenshot` tool calls — they return raw screenshots and don't invoke parsing.
- No new fallback path is introduced. If local parsing fails, the action fails — there is no silent degrade to LLM-guessed coordinates (see "Removed fallback" below).

## Architecture

### Data flow

**Today:** LLM calls `click`/`hover`/`drag` with a text description → `find_element_coordinates()` → screenshot dispatched to `controller_client` over WebSocket → raw image returned → Django HTTP-POSTs the image to the central `omniparser_service` → parsed result (annotated image + element list) returns over HTTP → LLM picks the matching element from the result.

**New:** LLM calls `click`/`hover`/`drag` → single new WebSocket dispatch (`find_element`) to `controller_client` → the controller takes its own screenshot and runs OmniParser **in-process** (device auto-detected: `cuda` → `mps` → `cpu`) → replies with the parsed result directly over the existing WebSocket connection → LLM picks the matching element. One round trip, no HTTP hop, no central service.

### Protocol change

A new controller action, `find_element`, following the existing `controller_*` dispatch pattern already used for `screenshot_request`/`click`/etc. (`_dispatch_controller_action` in `projects/services.py` → `ControllerConsumer` → controller's message loop → reply routed back via `ReplyTracker`):

- Request (server → controller): `{"type": "find_element", "request_id": ..., "timestamp": ..., "box_threshold": <float, optional>, "iou_threshold": <float, optional>}`. Thresholds are optional; the controller applies its own configured defaults when omitted.
- Response (controller → server): same shape as today's `PixelParseResult` — `{"success": bool, "image_width": int, "image_height": int, "annotated_image_base64": str, "elements": [{"index": int, "type": str, "content": str, "bbox": {...}, "center_x": float, "center_y": float, "interactivity": bool}], "error": <str, optional>}`.

Since `controller_client` is a standalone codebase with no shared import path to the Django `agents` app, this schema is mirrored on both sides — a dataclass in `controller_client/protocol.py`, and the existing `agents/types.py` `PixelParseResult`/`PixelUIElement`/`PixelBBox` on the server. This mirroring is the existing pattern for every message type in this protocol; nothing new is introduced here.

### Controller client changes

- New `controller_client/omniparser/` package, structured like the existing `executor.py`/`browser_executor.py`:
  - The Microsoft OmniParser vendored util code (currently at the Django repo root, `OmniParser/`, ~3.1MB, no weights) moves wholesale into `controller_client/omniparser/`. It's removed from the Django repo root — it no longer belongs there once the central service is gone.
  - A singleton model loader with device auto-detection: `torch.cuda.is_available()` → `"cuda"`, else `torch.backends.mps.is_available()` → `"mps"`, else `"cpu"`.
  - The model (YOLO icon detector + Florence-2 captioning + EasyOCR) loads **lazily on first `find_element` request**, not at controller startup, and is cached in-process for the rest of the session. Trade-off: the first click/hover/drag of a session incurs a one-time load latency (potentially several seconds to tens of seconds depending on device); every subsequent call in that session reuses the loaded model.
  - A new `execute_find_element()` function, mirroring `execute_screenshot()`: takes a screenshot internally, runs detection/captioning/OCR, returns the `PixelParseResult` payload.
  - Because `controller_client`'s message loop is asyncio-based (via `websockets`) and model inference is a blocking call, `execute_find_element()` runs via `loop.run_in_executor(...)` so parsing doesn't freeze the WebSocket connection (pings, concurrent commands) while it runs.

### Packaging & platform-aware install

- `controller_client/requirements.txt` gains the OmniParser dependency stack: `torch`, `torchvision`, `ultralytics`, `easyocr`, `paddleocr`/`paddlepaddle`, `transformers`, `accelerate`, `timm`, `supervision`, `opencv-python-headless` — mirroring `omniparser_service/requirements.txt` today.
- This is bundled by default for every install — no opt-in step, no separate extras file.
- `torch` itself needs a platform-appropriate wheel. The setup scripts (`setup.sh`/`setup.ps1`/`setup.bat`) detect OS + NVIDIA GPU presence at install time and select the CUDA wheel index on Linux/Windows with a detected GPU, otherwise the default wheel (CPU on Linux/Windows; the standard macOS wheel, which already includes MPS support, needs no special index). This mirrors what the current Dockerfile already does for the central service, just decided per end-user machine instead of a fixed GPU box.
- Model weights (~1.5GB) download during setup, via a script adapted from today's `scripts/download_omniparser_weights.sh`, moved to `controller_client/scripts/`. Weights are stored in a gitignored directory inside `controller_client/`, self-contained with the rest of the client.
- Setup failure (weight download or dependency install) hard-fails the setup script, consistent with how other steps (e.g. `playwright install --with-deps`) already abort on failure. No silent partial install.

### Server-side changes

- `projects/services.py` gains `controller_find_elements(project_id, box_threshold=None, iou_threshold=None)`, following the same `_dispatch_controller_action` pattern as `controller_screenshot`/`controller_click`.
- `agents/services/controller_element_finder.py` and `agents/services/controller_omniparser_element_finder.py` merge into a single module. The `is_omniparser_configured()` branch and the vision-LLM-guess-coordinates fallback are removed entirely — there is now exactly one path: call `controller_find_elements()`, then use the LLM to pick the best-matching element from the returned annotated image + element list.
- `agents/services/omniparser_client.py` (the HTTP client) is deleted.
- `agents/types.py`'s `PixelParseResult`/`PixelUIElement`/`PixelBBox` are unchanged — same types, now populated from the controller's WebSocket reply instead of an HTTP response.

### Removed entirely

- `omniparser_service/` — the FastAPI app, `Dockerfile`, `docker-compose.gpu.yml`, its `requirements.txt`, its weight-download script.
- The root vendored `OmniParser/` directory (moved into `controller_client/omniparser/`, not left duplicated).
- Settings: `OMNIPARSER_URL`, `OMNIPARSER_API_KEY`, `OMNIPARSER_REQUEST_TIMEOUT` from `auto_tester/settings.py`, `.env`, and `example.env`.
- Any `docker-compose.yml` entries referencing `omniparser_service`.
- `docs/specs/007.9. VNC click issue.md` (the spec that originally introduced the central service) is left untouched as historical record.

### Removed fallback

Today, `find_element_coordinates()` falls back to asking the vision LLM to guess raw coordinates directly when OmniParser isn't configured. Since OmniParser now ships by default with every `controller_client` install, this fallback is removed. If local parsing fails at runtime (model load error, inference exception), the action fails with a real error — it does not silently degrade to a guess.

## Error Handling

- Model load failure, weight-loading errors, or inference exceptions on the controller: `find_element` replies `{success: false, error: "..."}`, using the same error-reply shape already used by other controller actions. This surfaces as a real tool-call error through `find_element_coordinates` → `tool_registry` → the agent loop, same as any other failed action today (e.g. a failed click).
- Timeout: reuses the existing `reply_timeout` / `asyncio.wait_for` mechanism already in `_dispatch_controller_action` — no new timeout handling needed.
- Setup-time weight download or dependency install failure: setup script hard-fails, consistent with existing setup steps.

## Testing Plan

Per this project's E2E-only testing convention (no pytest, no mocks):

- **`logic-tester`**: exercise the new protocol path directly — connect a real `controller_client`, invoke `controller_find_elements()` via Django shell/service call, verify the returned `PixelParseResult` shape and that coordinates are sane against a known screenshot. Verify the error path (forced failure) propagates a clean error without crashing the WebSocket connection or the Django caller.
- **`nightmare-tester`**: run a real test case through the UI requiring native `click`/`hover`/`drag` (so it must go through OmniParser element-finding) end-to-end, confirming clicks land on the correct element and results render correctly in the UI.
- **Manual/`linux-master`-assisted**: run the updated setup script on a clean environment, confirm the platform-appropriate torch wheel installs, weights download successfully, and a sample `find_element` call parses a screenshot correctly (this development machine is a Mac, exercising the MPS path).

Screenshots and any test users created during E2E testing are deleted after testing completes, per project convention.
