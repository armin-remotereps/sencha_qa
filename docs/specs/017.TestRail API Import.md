# 017. TestRail API Import

Import test cases straight from a TestRail account over its REST API, in
addition to the existing TestRail XML upload.

## Goals

- Per-project TestRail connection settings (URL, account email, API key).
- One click on the project imports a TestRail suite into the project's test
  cases, with the same live progress and import history the XML upload has.
- Re-importing refreshes cases already in the project instead of duplicating
  them.

## Non-goals

- Writing anything back to TestRail. (Superseded by 018 — TestRail Results
  Export adds result pushing; the import itself stays read-only.)
- Importing by section subtree, run, or milestone.
- Scheduled or automatic syncs.
- Replacing the XML upload. It stays as-is.

## Verified facts about the TestRail API (sencha.testrail.com, 2026-09-14)

- Base URL: `{testrail_url}/index.php?/api/v2/{method}`. HTTP Basic auth with
  `email:api_key`. `Content-Type: application/json`. Auth failures return
  `401 {"error": "Authentication failed: ..."}`.
- `get_projects` is paginated: `{offset, limit, size, _links: {next, prev},
  projects: [...]}`. `size` is the page size, not the total. Each project has
  `id`, `name`, `suite_mode` (1 = single suite, 2 = single suite + baselines,
  3 = multiple suites), `is_completed`.
- `get_suites/{project_id}` is paginated the same way under `suites`. A
  single-suite project has exactly one suite (`is_master: true`).
- `get_cases/{project_id}&suite_id={suite_id}&limit=250&offset=N` is paginated
  under `cases`. `suite_id` is required for multi-suite projects and accepted
  for single-suite ones. No total count is returned; follow `_links.next`
  until it is `null`.
- `get_case_types` and `get_priorities` are plain lists. Type names match the
  `TestCaseType` choices exactly. Priority names match `TestCasePriority`
  except `"1 - Do Not Test"` (TestRail) vs `"1 - Don't Test"` (model).
- A case carries `id`, `title`, `section_id`, `suite_id`, `template_id`,
  `type_id`, `priority_id`, `refs`, `estimate`, `custom_preconds`,
  `custom_steps`, `custom_expected`, `custom_steps_separated` (list of
  `{content, expected}` used by the "Test Case (Steps)" template) plus other
  custom fields that are ignored. Text fields are TestRail markdown or HTML
  and are stored as-is, exactly as the XML import does.
- TestRail Cloud rate limit is 180 requests per minute; over-limit requests
  return `429` with a `Retry-After` header.

## Data model

### `Project` (new fields)

| Field | Type | Notes |
|---|---|---|
| `testrail_url` | `URLField(max_length=500, blank=True, default="")` | Normalized without trailing slash on save. |
| `testrail_email` | `EmailField(blank=True, default="")` | Login email that owns the API key. |
| `testrail_api_key_encrypted` | `TextField(blank=True, default="")` | Fernet token. Never rendered. |

Property `has_testrail_settings` is true when all three are non-empty.

### API key encryption

- New setting `FIELD_ENCRYPTION_KEY` (read via `python-decouple` in
  `settings.py`, documented in `example.env`). It is a urlsafe base64 Fernet
  key. Startup fails loudly if it is missing or malformed.
- `projects/secrets.py` (utility module, no ORM): `encrypt_secret(str) ->
  str` and `decrypt_secret(str) -> str` wrapping `cryptography.fernet.Fernet`.
- `cryptography` is pinned in `requirements.txt` (already installed
  transitively).

### `TestCaseUpload` (reused as the import history row)

| Field | Change |
|---|---|
| `source` | new `CharField` with choices `xml` (default) / `testrail_api` |
| `file` | becomes `blank=True` (API imports have no file) |
| `testrail_project_id` | new `PositiveIntegerField(null=True, blank=True)` |
| `testrail_suite_id` | new `PositiveIntegerField(null=True, blank=True)` |
| `updated_cases` | new `PositiveIntegerField(default=0)` |

For API imports `original_filename` holds the display label
`"TestRail: {project name} / {suite name}"` so the import history table and
the "Import" filter on the Test Cases page keep working unchanged.

Existing rows get `source="xml"` via the field default.

## TestRail client (`projects/testrail_client.py`)

- `TestRailClient(url, email, api_key, timeout)` built on `httpx.Client`
  with Basic auth. Constructed only through `build_testrail_client(project)`
  in the service layer, which decrypts the key.
- Typed dataclasses: `TestRailProject(id, name, suite_mode, is_completed)`,
  `TestRailSuite(id, name, is_master)`, `TestRailCaseType(id, name)`,
  `TestRailPriority(id, name)`, `TestRailCase(id, title, template_id,
  type_id, priority_id, refs, estimate, preconditions, steps, expected,
  steps_separated)`.
- Methods: `get_projects()`, `get_suites(project_id)`,
  `iter_cases(project_id, suite_id)` (generator following `next` links at
  250 per page), `get_case_types()`, `get_priorities()`. Also used by the
  settings services: `check_testrail_connection`.
- Errors: one `TestRailError(message, status_code)`. `401`/`403` surface the
  TestRail message; `429` is retried up to 3 times honoring `Retry-After`
  before raising; network errors and invalid JSON are wrapped as
  `TestRailError` with status `0`.
- Completed TestRail projects (`is_completed`) are returned but the picker
  lists them last, labeled "(completed)".

## Settings tab

- New fifth project tab **Settings** (`projects:settings`,
  `/<project_id>/settings/`) rendered by `templates/projects/settings.html`
  (`active_tab="settings"`; `partials/project_tabs.html` and
  `layouts/project.html` contract updated).
- One card, **TestRail integration**, with `TestRailSettingsForm`:
  - `testrail_url` (required when saving, must be `https://` or `http://`).
  - `testrail_email` (required).
  - `testrail_api_key` (password input; required on first save, optional
    afterwards). Empty means "keep the current key". The hint shows
    "Saved key ends in …{last 3 chars}" when one exists.
  - Save posts to the same URL. Service: `save_testrail_settings(project=,
    url=, email=, api_key=)` (api_key `None` keeps the stored key).
- **Test connection** button posts to `projects:settings_testrail_test`
  (`/<project_id>/settings/testrail/test/`). Service
  `check_testrail_connection(project) -> TestRailConnectionResult(ok,
  message, project_count)`; the view maps it to `messages.success` /
  `messages.error` and redirects back to Settings.
- **Clear settings** button posts to `projects:settings_testrail_clear` and
  blanks all three fields (confirm dialog, `dialog()` convention).
- Both views use `@project_membership_required` + `@require_POST`.

## Import flow

All server-rendered, no JSON endpoints.

1. **Import page** (`projects:test_case_import`) gains a card **Import from
   TestRail account** above the XML dropzone.
   - Without settings: the card explains and links to the Settings tab.
   - With settings: the view calls `get_testrail_picker_state(project) ->
     TestRailPickerState(configured, projects, error)`; projects are cached
     in the Django cache for 5 minutes under `testrail_projects:{project_id}`
     and invalidated when settings are saved or cleared. On `TestRailError`
     the state carries the error text and the card shows it with a link to
     Settings; the page still renders the XML card and history.
   - Form: `<select name="testrail_project_id">` + **Continue**.
2. **POST `projects:testrail_import_start`**
   (`/<project_id>/test-cases/import/testrail/`), `TestRailImportStartForm`
   validates `testrail_project_id` is an int.
   - Service `resolve_testrail_import(project, testrail_project_id) ->
     TestRailImportResolution(testrail_project, suites)` fetches the
     TestRail project and its suites; `single_suite` is the lone suite for
     single-suite projects and `None` for multi-suite ones.
   - Single-suite: `start_testrail_import(project=, user=, target=)` creates
     the `TestCaseUpload` row (`source=testrail_api`, label, ids,
     `status=PROCESSING`) and dispatches the task; redirect to the Import
     page.
   - Multi-suite: render `templates/projects/testrail_suite_picker.html`
     with a `<select name="testrail_suite_id">` and **Import** posting to
     `projects:testrail_import_suite`
     (`/<project_id>/test-cases/import/testrail/<int:testrail_project_id>/`),
     which calls `resolve_testrail_import_suite(project,
     testrail_project_id, suite_id) -> TestRailImportTarget` (validates the
     suite belongs to that project) and then `start_testrail_import`.
   - Any `TestRailError` becomes `messages.error` + redirect to the Import
     page.
3. **Test Cases page header**: the existing "Import from TestRail" button is
   unchanged; the Import page now offers both routes.

## Celery task `projects.tasks.import_testrail_cases`

- Queue `upload`, same options as `process_xml_upload` (`acks_late`,
  `reject_on_worker_lost`, `max_retries=0`, `soft_time_limit=600`,
  `time_limit=660`).
- Steps, all delegated to services:
  1. Fetch vocabularies (`get_case_types`, `get_priorities`) and build a
     `TestRailFieldMapper`.
  2. Collect all cases via `iter_cases` into a list; set `total_cases` and
     broadcast progress.
  3. `upsert_test_cases_from_testrail(upload=, project=, cases=, mapper=,
     batch_size=50, progress_callback=)`:
     - Load existing `TestCase` rows of the project whose `testrail_id` is in
       the batch (as strings).
     - Existing rows (all duplicates, if any) are updated in place with the
       mapped fields; `upload` FK is left untouched; counted in
       `updated_cases`.
     - Missing rows are bulk-created with `upload=<this import>`.
     - After each batch `processed_cases` advances by the batch size
       (created + updated) and progress is broadcast.
  4. Mark completed and broadcast.
- Progress: `processed_cases` counts cases handled (created or updated) so
  the existing progress bar semantics (`processed / total`) hold;
  `updated_cases` is additional and shown in the history table as
  "N new · M updated" for API rows.
- Failure: status `FAILED`, `error_message` = TestRail message when the
  cause is `TestRailError`, else the generic message; delete only
  `upload.test_cases` (the rows this import created). Updates already applied
  to pre-existing rows are not rolled back (documented behaviour).
- Cancel (`cancel_upload_processing`) is unchanged: revoke, delete the rows
  this import created, mark cancelled.

## Field mapping (`projects/testrail_mapping.py`, pure functions)

| TestRail | TestCase | Rule |
|---|---|---|
| `id` | `testrail_id` | `str(id)` |
| `title` | `title` | truncated to 500 chars |
| `template_id` | `template` | No `get_templates` lookup. `"Test Case (Steps)"` when `steps_separated` is non-empty, otherwise `"Test Case"`. |
| `type_id` | `type` | name via `get_case_types`; unknown → `TestCaseType.FUNCTIONAL` |
| `priority_id` | `priority` | name via `get_priorities`; `"1 - Do Not Test"` → `TestCasePriority.DONT_TEST`; unknown → `TestCasePriority.MUST_TEST_HIGH` |
| `estimate` | `estimate` | `""` when null, truncated to 50 |
| `refs` | `references` | `""` when null, truncated to 500 |
| `custom_preconds` | `preconditions` | as-is, `""` when null |
| `custom_steps` / `custom_steps_separated` | `steps` | if `steps_separated` non-empty: `"1. {content}\n\n2. ..."`; else `custom_steps` |
| `custom_expected` / `custom_steps_separated` | `expected` | if `steps_separated` non-empty: `"1. {expected}\n\n2. ..."` (only non-empty entries); else `custom_expected` |
| — | `is_converted` | `False` |

## Security

- Settings and import views require login and project membership
  (`@project_membership_required`); mutations are `@require_POST` with CSRF.
- API key encrypted at rest, never logged, never rendered; the TestRail URL
  must be http(s) to prevent SSRF into other schemes. Outbound requests go
  only to the configured URL.
- TestRail error messages are rendered through Django's autoescaping.

## Testing (unit, no live calls)

- `testrail_client`: pagination follows `next`; `suite_id` passed; `401`
  → `TestRailError` with message; `429` retried then raised; bad JSON
  wrapped. Uses `httpx.MockTransport`.
- `secrets`: encrypt/decrypt round trip; decrypt of garbage raises.
- `testrail_mapping`: every row of the table above, including the priority
  mismatch, unknown ids, `steps_separated` flattening, truncation.
- services: `save_testrail_settings` keeps the key when `None`, URL
  normalization, cache invalidation; `resolve_testrail_import`
  single vs multi suite; `upsert_test_cases_from_testrail` creates vs
  updates, keeps original `upload` FK on updates, counts, progress callback.
- task: success path marks completed with counts; `TestRailError` marks
  failed with its message and deletes only created rows.
- views: anonymous → login redirect; non-member → 404/403 as the decorator
  does today; settings save with/without key; test connection success and
  failure messages; import start redirects on missing settings; suite
  picker renders for multi-suite.

## Out of scope but noted

- Deduplicating pre-existing duplicate `testrail_id` rows.
- Per-user (rather than per-project) TestRail credentials.
