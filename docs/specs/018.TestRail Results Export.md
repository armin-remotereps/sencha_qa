# 018. TestRail Results Export

Push the results of a finished run back to TestRail over its REST API, the
reverse direction of 017 (TestRail API Import).

## Goals

- One button on a finished run pushes every Passed/Failed case result to a
  TestRail run.
- The first push creates the TestRail run and remembers it; later pushes of
  the same run reuse it.
- A re-push only sends results that changed since the last push. Unchanged
  results are skipped.
- Push status (pushing / pushed at / failed with the TestRail message) is
  visible on the run page and updates live.

## Non-goals

- Pushing screenshots or logs as attachments.
- Pushing cancelled, not started or running cases.
- Pushing into an existing, user-chosen TestRail run or test plan.
- Project-level "push every run" action.
- Scheduled or automatic pushes.

## Verified facts about the TestRail API (v2)

- Results are append-only. `add_results_for_cases` appends a new result per
  case; there is no update-result endpoint. "Update if changed" therefore
  means appending a new result, and "ignore" means skipping the case.
- `POST add_run/{project_id}` with `{suite_id, name, description,
  include_all: false, case_ids}` returns the run (`id`, `is_completed`,
  `url`). `suite_id` is required for multi-suite projects and accepted for
  single-suite ones.
- `GET get_run/{run_id}` returns the run; deleted runs answer 400/404.
- `POST update_run/{run_id}` with `{include_all: false, case_ids}` replaces
  the run's case set.
- `POST add_results_for_cases/{run_id}` with `{results: [{case_id,
  status_id, comment, elapsed}]}` returns the created results in request
  order (`id`, `status_id`, `test_id`).
- `elapsed` is a timespan such as `"1h 2m 3s"` and must be at least 1s; the
  key is omitted otherwise.
- Built-in status ids: 1 Passed, 5 Failed.
- Auth, rate limiting (429 + `Retry-After`) and the `{"error": ...}` envelope
  behave as documented in 017.

## Data model

### `TestRun` (new fields)

| Field | Type | Notes |
|---|---|---|
| `testrail_project_id` | `PositiveIntegerField(null=True, blank=True)` | chosen on first push |
| `testrail_suite_id` | `PositiveIntegerField(null=True, blank=True)` | chosen on first push |
| `testrail_run_id` | `PositiveIntegerField(null=True, blank=True)` | TestRail run created by the first push |
| `testrail_push_status` | `CharField` choices `not_pushed` (default) / `pushing` / `pushed` / `failed` | |
| `testrail_pushed_at` | `DateTimeField(null=True, blank=True)` | last successful push |
| `testrail_push_error` | `TextField(blank=True, default="")` | TestRail message of the last failure |
| `testrail_push_summary` | `CharField(max_length=255, blank=True, default="")` | "12 results pushed · 3 unchanged · 1 without a TestRail ID" |

Property `has_testrail_target` is true when project and suite ids are set.

### `TestRunTestCase` (new fields, what was last pushed)

| Field | Type |
|---|---|
| `testrail_result_id` | `PositiveIntegerField(null=True, blank=True)` |
| `testrail_pushed_status_id` | `PositiveSmallIntegerField(null=True, blank=True)` |
| `testrail_pushed_comment_hash` | `CharField(max_length=64, blank=True, default="")` |
| `testrail_pushed_at` | `DateTimeField(null=True, blank=True)` |

`reset_test_run` sets `testrail_push_status` back to `not_pushed` and blanks
`testrail_pushed_at`, `testrail_push_error` and `testrail_push_summary`. It
keeps `testrail_run_id` and the per-case tracking, so a re-run with the same
outcome is still skipped and a different outcome appends to the same TestRail
run.

## Mapping

| Punk Hazard | TestRail | Rule |
|---|---|---|
| `TestRunTestCase.status == success` | `status_id = 1` (Passed) | |
| `TestRunTestCase.status == failed` | `status_id = 5` (Failed) | |
| any other status | — | skipped, counted as "not pushable" |
| `TestCase.testrail_id` | `case_id` | `"123"` and `"C123"` accepted; anything else skipped, counted as "without a TestRail ID" |
| `started_at`/`finished_at` | `elapsed` | `"1h 2m 3s"`; omitted when unknown or under 1s |
| `TestRunTestCase.result` | `comment` | `"{Passed|Failed} by Punk Hazard in run “{run name}”."`, blank line, result text truncated to 4000 characters, blank line, `"Details: {absolute case detail URL}"` |

A case is **changed** when its `status_id` or the SHA-256 of its comment
differs from the values stored on the pivot by the previous push.

## Flow

1. Run detail page, finished run, TestRail configured on the project:
   **Push to TestRail** button.
   - Run has no TestRail target yet: a dialog lists the TestRail projects
     (same cached picker as the import), preselecting the project most of
     the run's cases were imported from. **Continue** posts to
     `projects:testrail_push_start`. Multi-suite projects then show the
     suite picker page (shared with the import flow) posting to
     `projects:testrail_push_suite`. The chosen project/suite is stored on
     the run and the push starts.
   - Run already has a target: a confirm dialog ("Push N changed results to
     TestRail run R{id}?") posts to `projects:testrail_push_start` with no
     project id. The button is disabled when nothing changed or a push is
     in progress.
   - TestRail not configured: a muted line links to Settings.
2. The view marks the run `pushing`, broadcasts, and dispatches the Celery
   task `projects.tasks.push_test_run_results(test_run_id, links_base_url)`
   on the `upload` queue. `links_base_url` is
   `request.build_absolute_uri("/")` so comments can link back.
3. The task:
   1. Plans the push (one query over the run's pivots + cases).
   2. Ensures the TestRail run: none → `add_run` named
      `"Punk Hazard: {run display name}"` with the pushable case ids;
      existing → `get_run`; deleted or completed → a fresh run is created
      and the per-case tracking for this run is cleared so every result is
      pushed again; otherwise `update_run` with the union of pushable case
      ids and previously pushed case ids.
   3. Sends changed results in batches of 100 via `add_results_for_cases`
      and stores result id, status id, comment hash and timestamp on each
      pivot after every batch.
   4. Marks the run `pushed` with `testrail_pushed_at` and the summary, or
      `failed` with the TestRail message. Both broadcast on the run's
      WebSocket group; the page reloads once to show the server-rendered
      status.

## Security

- Both push views require login and project membership
  (`@project_membership_required`) and are `@require_POST` with CSRF.
- Only the project's stored TestRail URL is contacted. The API key is
  decrypted only inside the service layer, never logged or rendered.
- Result text is sent as a TestRail comment as-is; TestRail renders its own
  markdown. Links use the request host, which is validated by
  `ALLOWED_HOSTS`.

## Testing (unit, no live calls)

- Client: `add_run`, `update_run`, `add_results_for_cases` payloads, elapsed
  omission, response length mismatch, 429 retry and error envelope on POST.
- Mapping: status map, case id parsing, elapsed formatting, comment content
  and truncation, hash stability.
- Services: changed vs unchanged detection, skip counters, target
  suggestion, first push creates and stores the run, second push reuses and
  pushes only changes, closed/deleted run recreation, start guards,
  `reset_test_run` behaviour.
- Task: success and failure stamping.
- Views: auth, membership, target handling, suite picker, error messages,
  run detail rendering of the button and status line.
