Phone or tablet type

The host computer can be Windows, macOS or Linux. A real phone, a tablet or an Android emulator all work.

  1. Set up the Test Runner on the host computer

    Download the ZIP above and run the setup script for the host's operating system, as for a desktop test machine. Do not start it yet.

  2. Install Node.js, Appium and its Android driver on the host

    Node.js 22.22.2 or newer (or 24.15+), then:

    npm i -g appium@3
appium driver install uiautomator2
  3. Install the Android platform tools

    Through Android Studio → SDK Manager, brew install android-platform-tools on macOS, or winget install Google.PlatformTools on Windows. adb must be on PATH, and Appium's Android driver needs ANDROID_HOME set to the folder that contains platform-tools, in the terminal that starts the Test Runner. Android Studio's SDK is usually ~/Library/Android/sdk (macOS), ~/Android/Sdk (Linux) or %LOCALAPPDATA%\Android\Sdk (Windows).

    export ANDROID_HOME="$HOME/Library/Android/sdk"   # macOS, in ~/.zshrc
export ANDROID_HOME="$HOME/Android/Sdk"           # Linux, in ~/.bashrc
setx ANDROID_HOME "%LOCALAPPDATA%\Android\Sdk"    # Windows Command Prompt, then open a new terminal
adb version

    In PowerShell use setx ANDROID_HOME "$env:LOCALAPPDATA\Android\Sdk". If you installed only the platform tools (brew, winget), set it to the folder that holds their platform-tools folder instead.

  4. Turn on USB debugging on the phone

    Settings → About phone → tap Build number seven times to unlock Developer options. Then Settings → System → Developer options → turn on USB debugging. The exact menu names differ a little between phone makers.

  5. Connect the phone and allow this computer

    Connect it with a USB cable, unlock it and tap Allow on the "Allow USB debugging?" prompt (tick "Always allow from this computer"). The phone must show as device, not unauthorized:

    adb devices -l
  6. Point the Test Runner at Android

    In controller_client/.env:

    CONTROLLER_TARGET=android
CONTROLLER_DEVICE=

    Leave CONTROLLER_DEVICE blank: the first start from a terminal lists the connected devices, asks which one to drive and saves its serial. With several devices connected (a phone and an emulator, say), set it yourself before the check below, to the serial from adb devices -l. Leave CONTROLLER_APPIUM_URL blank so the Test Runner starts and stops its own Appium.

  7. Check, then start the Test Runner
    controller_client/.venv/bin/python -m controller_client.diagnose --mobile
controller_client/.venv/bin/python -m controller_client.main

    On Windows use controller_client\.venv\Scripts\python. The check asks before it taps the centre of the screen. Keep the phone unlocked and connected while tests run; the Connection card shows "Phone disconnected" when it is not.

  8. Browsers on the phone (optional)

    Chrome and Edge need no setup: open the app on the phone. For Firefox, turn on Firefox → Settings → Remote debugging via USB.

iPhones and iPads need a Mac as the host computer, with Xcode. A Simulator needs no signing: skip steps 4 and 5, and leave the CONTROLLER_IOS_* keys of step 6 blank.

  1. Set up the Test Runner on the Mac

    Download the ZIP above and run bash controller_client/scripts/setup.sh. Do not start it yet.

  2. Install Xcode, Node.js, Appium and its iOS driver

    Install Xcode from the App Store and open it once to accept the licence. Then Node.js 22.22.2 or newer (or 24.15+), and:

    npm i -g appium@3
appium driver install xcuitest
  3. Prepare the iPhone

    Connect it with a cable, unlock it and tap Trust This Computer. Then on the iPhone:

    • Settings → Privacy & Security → Developer Mode on (the iPhone restarts; confirm again).
    • Settings → Developer → Enable UI Automation on.
    • Settings → Accessibility → Zoom off (otherwise taps land in the wrong place).
  4. Add your Apple ID to Xcode and find your Team ID

    Xcode → Settings → Accounts → + → Apple ID. A free Apple ID works; a paid Apple Developer account avoids the 7-day re-signing below. List your signing certificates to get the exact certificate name:

    security find-identity -v -p codesigning

    Each line looks like "Apple Development: you@example.com (ABCDE12345)". The value in brackets is not the Team ID. The Team ID (10 characters) is the OU value of that certificate; use the name from the line above:

    security find-certificate -c "Apple Development: you@example.com" -p | openssl x509 -noout -subject

    For a paid account it is also shown on developer.apple.com → Account → Membership.

  5. Sign WebDriverAgent once in Xcode

    Appium installs WebDriverAgent (WDA) on the iPhone to drive it, and iOS only runs it signed by your team. Open the WDA project that came with Appium's iOS driver:

    WDA_PROJECT="$(find "${APPIUM_HOME:-$HOME/.appium}" -maxdepth 6 -name WebDriverAgent.xcodeproj | head -n 1)"
if [ -z "$WDA_PROJECT" ]; then echo "WebDriverAgent not found: run 'appium driver install xcuitest' first"; else mkdir -p "$(dirname "$WDA_PROJECT")/Resources/WebDriverAgent.bundle" && open "$WDA_PROJECT"; fi

    In Xcode:

    1. Select the project, then the WebDriverAgentRunner target → Signing & Capabilities.
    2. Tick Automatically manage signing and pick your Team.
    3. Change Bundle Identifier from com.facebook.WebDriverAgentRunner to one only you use, e.g. com.yourname.WebDriverAgentRunner. A free Apple ID must change it; Apple refuses the default.
    4. Do the same Team on the WebDriverAgentLib target if Xcode shows a signing error there.
    5. Product → Scheme → WebDriverAgentRunner; Product → Destination → your iPhone; then Product → Test (⌘U). This builds WDA and installs it on the iPhone. Stop the test once the iPhone shows WebDriverAgent running (a blank screen or the home screen is fine).

    If the iPhone says the developer is not trusted (free Apple ID): Settings → General → VPN & Device Management → Developer App → your Apple ID → Trust → Allow (the iPhone needs internet for this), then run Product → Test again.

  6. Point the Test Runner at the iPhone

    In controller_client/.env, with your Team ID and the Bundle Identifier from step 5:

    CONTROLLER_TARGET=ios
CONTROLLER_DEVICE=
CONTROLLER_IOS_TEAM_ID=XXXXXXXXXX
CONTROLLER_IOS_SIGNING_ID=Apple Development
CONTROLLER_IOS_WDA_BUNDLE_ID=com.yourname.WebDriverAgentRunner

    Appium then signs and installs WDA itself whenever it needs to, with the same team and bundle identifier. Leave CONTROLLER_DEVICE blank: the first start from a terminal lists the connected devices, asks which one to drive and saves its UDID. With several devices connected (an iPhone and a booted Simulator, say), set it yourself before the check below, to the UDID shown in brackets by xcrun xctrace list devices (not the Identifier column of devicectl), or xcrun simctl list devices booted for a Simulator.

    Alternative: keep the WDA you installed in step 5 and never rebuild it (iOS 17 or newer). Set CONTROLLER_IOS_PREINSTALLED_WDA=true and CONTROLLER_IOS_WDA_BUNDLE_ID to the Bundle Identifier from step 5 (without .xctrunner); CONTROLLER_IOS_TEAM_ID is then not used. This needs Xcode 15 or newer, and WDA is then never rebuilt by Appium: re-sign it yourself in Xcode (step 5).

  7. Check, then start the Test Runner
    controller_client/.venv/bin/python -m controller_client.diagnose --mobile
controller_client/.venv/bin/python -m controller_client.main

    The first start builds WDA and can take several minutes; the Connection card shows "Phone starting" meanwhile. The check asks before it taps the centre of the screen. Keep the iPhone unlocked and connected while tests run.

  8. Re-sign every 7 days with a free Apple ID

    A free Apple ID's signature expires after 7 days and WDA stops launching. Run Product → Test in Xcode again (step 5), or restart the Test Runner so Appium rebuilds it (not with the preinstalled option: then only Xcode re-signs it). A paid Apple Developer account lasts a year.

  9. Browsers on the iPhone (optional)

    Settings → Apps → Safari → Advanced → Web Inspector on. For Chrome, also turn on its own Web Inspector setting in Chrome → Settings → Content Settings, then restart Chrome. Edge and Firefox are controlled through their pages when the app allows inspection, otherwise through what is on screen.
