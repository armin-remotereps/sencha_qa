{% extends "layouts/project.html" %} {% load project_extras %} {% comment %} Run case detail — live via testRunCaseLive, ported from the old (Tailwind-era) test_run_case_detail.html: same WS URL, same message types (current_state / log / screenshot / status), same DOM effects (log auto-scroll, screenshot list growing in place). The header badge and the "Edit test case" / "Remove from run" actions need the same live status as the body cards, so — as with test_run_detail.html — `block page` is overridden wholesale rather than split across page_header/project_content, so everything shares one `x-data="testRunCaseLive"` root. Context contract (projects.views.test_run_case_detail): project, test_run, pivot (TestRunTestCase, select_related test_case + test_run, screenshots prefetched), screenshots (list, same queryset), form (TestCaseForm, for the edit dialog's type/priority choices), can_edit, case_position (1-based index of this case within the run), case_total (total case count for the run), can_check (verdict reached and not checked), can_uncheck (checked and not yet sent to TestRail), source_run_url (TestRail URL of the source run the result was sent to; "" when not sent or TestRail unconfigured). can_send_testrail (TestRail configured and the case is failed, unsent and has a source TestRail run: "Send to TestRail" opens includes/_testrail_case_send_dialog.html, posting this pivot id + next to projects:test_run_cases_send_testrail, in any run status), testrail_send_no_source (TestRail configured and a failed case without a source TestRail run: a muted "Can't send" line instead). pivot.testrail_source_skip_reason is set when a send could not deliver the case (shown via includes/_checked_skip_reason.html). pivot.blocked_reason / pivot.get_blocked_reason_display are set only when status is "blocked"; the blocked message itself is pivot.result. The case WS `status` / `current_state` events carry blocked_reason and blocked_reason_label (empty unless blocked). Resume (continue this case in place, on this run): can_resume (bool, projects.run_resume_services.can_resume_case), resume_steps (list[ResumeStepOption]: step_num, description, passed; empty when the case has no checkpoint, so it resumes from the start), resume_form (CaseResumeForm with the from_step select, or None when resume_steps is empty), resumes (list[TestRunCaseResume], resumed_by loaded; the case's earlier outcomes, oldest first). Each row's `kind` is "resume" (Resume, from_step set or None for "from the start") or "rerun" (re-run from step 1 on this run via the run page's bulk bar; from_step is None). Both are listed in the "Earlier attempts" card. When a re-run or resume resets this case, the `status` WS event moves it from a finished status back to "created" and the page reloads once to drop the old screenshots (and, for a re-run, the old log) and show the new history row. Steps card: step_progress (projects.case_step_progress.StepProgressPayload, from projects.case_step_progress.pivot_step_payload), serialized with json_script as "initial-steps". The case WS `current_state`, `status` and `steps` messages carry the same payload under `steps`; the client replaces it wholesale and derives no status itself. Its text is LLM output: render it with x-text only. A row carried over from an earlier plan by a help-chat redesign has carried_from (earlier step number, else null) and carried_label ("Passed under the earlier plan as step k: …"); its history lists the earlier attempts ("Earlier plan · …"). earlier_plans (tuple[projects.case_step_progress.EarlierPlan]: version, reason, help_request_id, help_step_num (the earlier plan's step the case waited for help at), resume_step, steps (num, description, status_label, carried_to)): the plans replaced by redesigns, rendered server-side (the page reloads when the case leaves "need_help"). Need help: help_panel (projects.case_help_services.HelpPanel, or None unless the run is paused on this case; see includes/_case_help_card.html), help_form (CaseHelpResolutionForm), help_requests (list[CaseHelpRequest], oldest first, resolved_by loaded, its thread (auto-fix or help chat) prefetched as help_threads, its applied and discarded redesigns as decided_plan_revisions, oldest first), help_mode_form (RunHelpModeForm: the help mode select of the Resume case dialog, pre-set to the run's mode). The page reloads when the case moves into, out of, or stays in "need_help" (an auto-fix ended), since the help card is server-rendered. Your turn (Human in the loop): person_step_panel (projects.person_step_services.PersonStepPanel, or None unless the run is paused on this case's person step; see includes/_person_step_card.html, rendered while it is open or confirming), person_step_form (unbound PersonStepReportForm), person_step_question_form (unbound PersonStepQuestionForm, the card's Ask the AI form). Socket event "person_step_questions" ({person_step_id, questions}) is re-dispatched as the window event "person-step-questions" for the card's personStepAsk list. The page reloads when the case moves into, out of, or stays in "awaiting_person"; the abort dialog is also rendered for it. Result chat (projects.case_result_page.get_case_result_panel): can_discuss_result (bool: Passed / Failed / Blocked), result_thread_id (the case's non-archived result chat thread, or None), result_chat_blocker ("" or why the chat cannot take a message: a run of the project is Started), result_changes (list[CaseResultChange], APPLIED, newest first, decided_by loaded), current_result_change (the applied change that wrote the current result, or None), current_result_from_label (the result that change replaced, e.g. "Passed"; "" without one), pending_review_redesign (bool). "Discuss result" posts `text` (optional, at most 8000 characters) to machine_setup:result_chat_open. An Earlier attempts row of kind "redesign" is a re-run with a result-chat redesigned plan (from_step is the first step that was not carried). An earlier plan with is_review was replaced after a result review (plan.label says which). The page reloads when the case moves between two finished statuses (a person applied a result change), since these parts are server-rendered. Access: project_can_write (context processor) gates every write control — Check / Uncheck, Edit, Remove, Resume, Discuss result, Abort, the help and person-step cards' forms (passed in as can_write) and every dialog. A read-only member keeps the result, steps, log, screenshots, history and the "Go to result chat" link. user.is_superuser gates the Resume dialog's run mode select. {% endcomment %} {% block title %}{{ pivot.test_case.title }} · {{ test_run.display_name }} · {{ brand_name|default:"Punk Hazard" }}{% endblock %} {% block breadcrumb_extra %} {{ project.name }} › Runs › {{ test_run.display_name }} › {{ pivot.test_case.title }} {% endblock %} {% block page %}
